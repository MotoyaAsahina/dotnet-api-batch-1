## 1. パッケージ構成のレビュー

### 概要

プロジェクト構成、csproj、パッケージ、設定ファイルをひととおり確認し、問題点と改善案を洗い出した。

### 現状の実装

```
src/
├── DotnetApiBatch.Data/    エンティティ、EF Core の設定、AppDbContext、共通の絞り込み条件（*Queries）
├── DotnetApiBatch.Api/     ASP.NET Core Web API（Controllers / Features/<ドメイン> / Errors）
└── DotnetApiBatch.Batch/   Generic Host 上のコンソールアプリ（Hosting / Jobs / Repositories）
tests/
└── DotnetApiBatch.Data.Tests/   NetArchTest による依存関係のテスト
```

- 依存の向きは `Api` / `Batch` → `Data` の一方向。`Api` と `Batch` は互いに参照しない
- `Data` はドメインごとのフォルダー（`Customers` / `Catalog` / `Orders`）に分かれ、依存の向き（Orders → Customers / Catalog）をテストで確認している
- レビュー時点で、ビルドは警告 0・エラー 0、テストは 5 件すべて成功。脆弱性のあるパッケージはなかった

全体として構成はよく考えられていて、README に設計の理由がまとまっている。

### 指摘事項

| No | 優先度 | 内容 | 対応 |
|---|---|---|---|
| 1 | 中 | `Directory.Build.props` / `Directory.Packages.props` / `global.json` がない。共通の設定を 4 つの csproj に重複して書いていて、`Microsoft.Extensions.*` のバージョンもそろっていない | **対応済み**（[2 章](#2-ビルド設定とパッケージのバージョンの一元管理)） |
| 2 | 中 | EF Core 本体は Npgsql 経由で間接的に参照しているだけなので、最低バージョンの 10.0.4 から上がらない。EF Core のパッチが入らない | 未対応 |
| 3 | 中 | 依存ルールのテストが `Data` の中だけ。`Api/Features` の依存の向きや「コントローラーはリポジトリを直接使わない」を確認していない。各ドメインから `Data` 直下の型（`AppDbContext` など）への参照も禁止していない。`NetArchTest.Rules` 1.3.2 は 2021 年以降更新されていない | 未対応 |
| 4 | 低 | `Api` の `AppExceptionHandler` が、`Data` 経由で間接的に参照している Npgsql / EF Core の例外型に依存している。DB プロバイダーの選択が `Data` の中に閉じていない | 未対応 |
| 5 | 低 | Batch の SDK を `Microsoft.NET.Sdk.Worker` にすると、`appsettings` をコピーする設定と `using` を減らせる見込み（未検証） | 未対応 |
| 6 | 低 | テスト用パッケージが古い（Microsoft.NET.Test.Sdk、xunit.runner.visualstudio、coverlet.collector）。`xunit` 2.x から `xunit.v3` への移行も検討 | 未対応 |
| 7 | 参考 | `Api` はドメインごと、`Batch` は種類ごと（`Jobs` / `Repositories`）にフォルダーを分けていて、そろっていない | 未対応（[3 章](#3-ドメインの分け方と将来の-msa-化)で関連する提案あり） |

指摘 1 から対応することにした。それ以外は未対応のまま残課題とする（[8 章](#8-決定事項と残課題のまとめ)）。

## 2. ビルド設定とパッケージのバージョンの一元管理

### 概要

レビューの指摘 1 に対応した。各 csproj に重複して書いていたビルド設定と、ばらばらに指定していたパッケージのバージョンを、ルートのファイルでまとめて管理する。

### 現状の実装（対応前）

- `TargetFramework` / `Nullable` / `ImplicitUsings` を 4 つの csproj に同じように書いていた
- バージョンは各 `PackageReference` に書いていて、`Microsoft.AspNetCore.OpenApi` だけ 10.0.11、ほかの `Microsoft.Extensions.*` は 10.0.13 だった
- SDK のバージョンを固定していなかった

### 対応内容

| ファイル | 内容 |
|---|---|
| `Directory.Build.props`（新規） | `TargetFramework` / `Nullable` / `ImplicitUsings` を移動。`TreatWarningsAsErrors` を有効にした |
| `Directory.Packages.props`（新規） | Central Package Management を導入。全パッケージのバージョンをここで管理する |
| `global.json`（新規） | SDK を 10.0.400 以上の 10.0.x に固定（`rollForward: latestFeature`） |
| 各 csproj | 共通の設定と `Version` を削除し、プロジェクトに固有の設定だけにした |
| `README.md` | 上記の説明と、プロジェクトを追加するときの注意を追記 |

- `Microsoft.AspNetCore.OpenApi` を 10.0.13 に上げて、`Microsoft.Extensions.*` とそろえた
- csproj の文字コードと改行を、BOM なしの UTF-8・LF にそろえた（もともとは BOM の有無が混在し、Api の csproj は CRLF と LF が混在していた）

### 選択肢と注意点

- **`dotnet new` のテンプレートは Central Package Management に対応していない**：新しく作ったプロジェクトは csproj に `Version` が付き、そのままでは `NU1008` エラーになる。作成後に `Version` と共通の設定を削除する（README に手順を記載）
- **`dotnet add package` は対応している**：`Directory.Packages.props` にバージョンが自動で追加される
- **transitive pinning**（`CentralPackageTransitivePinningEnabled`）は今回は入れていない。指摘 2（EF Core 本体のバージョン）に対応するときに検討する

### 採用判断

**実施済み。** PR #1 でマージした（ブランチ `chore/central-build-settings`）。ビルドは警告 0・エラー 0、テストは 5 件成功、`dotnet list package` で全プロジェクトが指定どおりのバージョンを使っていることを確認した。

## 3. ドメインの分け方と将来の MSA 化

### 概要

今の構成は次の要件から決めている。この要件に照らして、現状の評価、今後の検討事項、ほかの構成案を検討した。

- API と Batch は Service / Repository のメソッドを共有しない。そのため、共通の依存先は Data だけで済んでいる
- Data の中のドメイン同士は JOIN することがある
- 以上から、Data の中のドメインごとに csproj を分けていない
- 将来、ドメインごとに分けて MSA にする可能性がある

### 現状の実装と評価

| 要件 | 現状の実装 | 評価 |
|---|---|---|
| API と Batch で Service / Repository を共有しない | 互いを参照せず、共通の依存先は `Data` だけ。`Data` がアプリに依存しないことはテストで確認している | ◎ |
| ドメインをまたいで JOIN できる | DbContext は 1 つ。ナビゲーションで JOIN する | ◎ |
| ドメインごとに csproj を分けない | フォルダー（名前空間）で分け、依存の向きはテストで固定 | ○ |
| 将来、ドメイン単位で MSA にする | 下記のとおり準備が足りない部分がある | △ |

最初の 3 つは小さく始める構成として妥当。課題は「将来の MSA 化」と「ドメインをまたぐ JOIN」が根本的にぶつかること。

#### 分割の段階

README には「フォルダーを移すだけでプロジェクトに分けられる」とあるが、これは csproj を分ける段階までの話で、MSA にはそのまま当てはまらない。

| 段階 | 分ける単位 | ドメインをまたぐ JOIN | 必要な作業 |
|---|---|---|---|
| ① 今 | 名前空間（フォルダー） | できる | なし |
| ② モジュラーモノリス | csproj（プロセスは 1 つ） | できる（同じ DB） | フォルダーの移動、プロジェクト参照の整理 |
| ③ MSA | プロセスと DB | できない | ナビゲーションを ID 参照に変える、外部キーを外す、別サービスの API を呼ぶ、トランザクションを結果整合にする |

②から③への移行の重さは、ドメインをまたぐ JOIN の量でほぼ決まる。

#### 今のコードでドメインをまたいでいる箇所

| 場所 | 内容 | 種類 | MSA にしたときの置き換え先 |
|---|---|---|---|
| Api `OrderRepository.GetDetailAsync` | `Customer.Name`、`Product.Name` を JOIN | 参照（表示） | 注文に名前を複製しておく、または API を組み合わせる |
| Api `OrderService.CreateAsync` | 顧客・商品が存在するかの確認と単価の取得（DB の外部キーでも保証） | 更新時の検証 | 別サービスの API を呼ぶ、またはイベントで受け取った複製を使う |
| Batch `OrderRepository.SumShippedSalesByProductAsync` | Orders × Catalog の集計 | 分析 | 集計用のデータ（Read Model、DWH など） |
| `db/init/01_schema.sql` | `orders.customer_id` などの外部キー | 制約 | 外部キーを外す |

#### 今後の検討事項

- **JOIN のルールを決める**：「参照と分析ではドメインをまたぐ JOIN を許し、更新ではドメインの外のデータに頼らない」。注文の単価を明細に残している（`unit_price`）のは、既にこの考え方になっている
- **アプリの軸とドメインの軸を分けて考える**：MSA ではドメインが先。Orders の処理は今 `Api/Features/Orders`、`Batch/Jobs`、`Batch/Repositories` に散らばっているので、`Batch` もドメインごとのフォルダーにすると切り出しやすくなる。売上集計は Orders と Catalog の両方にまたがるので、「レポート」という別のドメインとして扱うことも検討する
- **DB のスキーマをドメインごとに分ける**：今は全テーブルが `public`。`customers` / `catalog` / `orders` に分けると、テーブルを持っているドメインが分かり、ドメインをまたぐ SQL にも気づきやすくなる
- **依存ルールのテストを `Api` と `Batch` に広げる**（レビューの指摘 3）
- **MSA にするきっかけを決めておく**：②へ進む条件（コードの規模、ビルド時間、ドメインごとの担当）と、③へ進む条件（独立したデプロイ、スケールの要件の違い、障害の切り離し）を分けて README に書く

### ほかの構成案

| 案 | 構成 | メリット | デメリット | 要件との相性 |
|---|---|---|---|---|
| A. 今の構成 | 共通の `Data` と、アプリごとのロジック | 単純。JOIN が自由 | ドメインのロジックがアプリごとに散らばる。MSA にするときに組み替えが要る | ◎（今の時点） |
| B. Data だけドメインごとに分ける | `Data.Customers` / `Data.Catalog` / `Data.Orders` と、その上に DbContext 用の `Data` | 依存の向きをコンパイラーが保証する。変更が小さい | DbContext が全ドメインに依存するのは変わらない。MSA への効果は小さい | ○ |
| C. モジュラーモノリス（ドメイン × アプリ） | `Orders.Data` / `Orders.Api` / `Orders.Batch` など。ホストはモジュールを組み立てるだけ。ドメインをまたぐ呼び出しは `*.Contracts` を通す | MSA に最も近い。1 つのモジュールをそのまま 1 つのサービスとして切り出せる | csproj が増える。ドメインごとの DbContext や、ドメインをまたぐ参照の設計が要る | ○ |
| D. CQRS の考え方を入れる | 更新はドメインの中だけ。参照（画面・レポート）はドメインをまたいでよい | 「JOIN したい」と「MSA にしたい」の両立に最も効く | 参照と更新の二重管理になる。Read Model の同期が要る | ◎（A〜C と組み合わせる） |
| E. クリーンアーキテクチャ / オニオン | `Domain` / `Application` / `Infrastructure` | 層の責務がはっきりする | 「Service を共有しない」とぶつかる。この規模では層が多すぎる | △ |
| F. すぐに MSA にする | ドメインごとに独立したサービスと DB | デプロイとスケールを独立させられる | JOIN が使えない。分散トランザクション、運用、ローカル開発の負担が大きい | ×（時期が早すぎる） |

分ける必要が出たときは、B ではなく C に進むのがよい。B は Data しか分けないので、MSA に進むときにもう一度組み替えることになる。MSA は C で境界が保てていると確かめてから、モジュール単位で切り出す（複数サービスのローカル開発には .NET Aspire が使える）。

### 採用判断

**ドメインの分け方は今のまま（案 A）で進める。** 上の「今後の検討事項」（JOIN のルール、Batch のフォルダー、DB のスキーマ、テストの拡張、MSA のきっかけ）は未着手。

## 4. モジュラーモノリスでのドメイン間の JOIN

### 概要

ドメインでモジュラーモノリスにした場合、ドメイン間の JOIN は許されるか。

### 前提

モジュラーモノリスの前提は「各モジュールが自分のデータを持ち、ほかのモジュールは公開されたインターフェースからしか使わない」こと。ほかのモジュールのテーブルを直接 JOIN すると、テーブルの構造がインターフェースの代わりになり、次のことが起こる。

- 相手のモジュールの列名を変えると、自分のモジュールが壊れる
- MSA にするときに、JOIN している箇所をすべて書き直すことになる

技術的にも、EF Core ではモジュールごとに DbContext を分けると、別々の DbContext のクエリを 1 つにまとめられない（実行時に例外）。JOIN するには、両方のテーブルをマッピングした DbContext が必要になる。どこにその DbContext を置くかが設計の判断になる。

### 選択肢（許す範囲の段階）

| 段階 | 内容 | JOIN | MSA への移りやすさ |
|---|---|---|---|
| 1. 共有の DbContext | 今の構成のまま csproj だけ分ける | どこでも可 | × 分けた効果がほとんどない |
| 2. 公開ビューへの JOIN を許す | モジュールが公開ビュー（DB の VIEW、読み取り専用のエンティティ）を API の一部として公開する。内部のテーブルは見せない | 公開ビューに対してだけ可 | ○ ビューを API や複製に置き換えればよい |
| 3. 参照専用のモジュールで JOIN | Reporting / Query モジュールが、複数のスキーマをマッピングした読み取り専用の DbContext を持つ | そのモジュールの中だけ可 | ○ そのまま DWH や Read Model になる |
| 4. 複製する | 必要なデータを自分のモジュールに複製する（作成時に保存、またはイベントで同期） | 自分のモジュールの中だけ | ◎ |
| 5. 完全に禁止 | ID で参照し、ほかのモジュールのインターフェースを呼んでメモリー上で組み合わせる | 不可 | ◎ ただし、ドメインをまたいだ並べ替えやページングが難しい |

### このプロジェクトに当てはめた場合

| 用途 | 方針 | 今のコードで当てはまる箇所 |
|---|---|---|
| 更新（業務ルールの検証を含む） | JOIN しない。ID で参照し、相手のモジュールの公開インターフェースで確認する | `OrderService.CreateAsync` の存在確認と単価の取得 → `ICustomerLookup` / `IProductCatalog` を呼ぶ |
| 画面表示（1 件の詳細、少量の一覧） | 組み合わせ（段階 5）か複製（段階 4） | 注文詳細の顧客名・商品名 → ID でまとめて取得して組み合わせる、または注文時に名前も保存する |
| 集計とレポート | 参照専用のモジュールで JOIN してよい（段階 3） | 売上集計のジョブ → `Reporting` モジュールに移し、読み取り専用の DbContext で JOIN する |

補足：

- スキーマをまたぐ DB の外部キーは、モノリスの間は残してよい。MSA にするときに外す前提であることを記録しておく
- 1 つのトランザクションで複数のモジュールを更新するのも原則として避ける。必要になったら Outbox とイベントで連携する方法を検討する
- 「ほかのモジュールの `Contracts` 以外を参照しない」「ほかのモジュールの DbContext を参照するのは `Reporting` だけ」は NetArchTest で確認できる

### 採用判断

**JOIN は禁止ではなく、参照系に限って決めた場所でだけ使う。** ただし 3 章のとおり、ドメインの分け方は今のままにしたので、これは将来モジュラーモノリスにするときの指針として残す。

## 5. DbContext を API と Batch のそれぞれに置くか

### 概要

DbContext を `Data` で 1 つ共有するのではなく、API と Batch のそれぞれに用意することについて検討した。

### 現状の実装

- `Data` の `AppDbContext` を API と Batch で共有している
- アプリごとの違いは、`AddData(configuration, configureNpgsql)` の引数で渡している（Batch はコマンドのタイムアウトを 300 秒にしている）
- スキーマは `db/init/01_schema.sql` で管理していて、EF Core のマイグレーションは使っていない

### 選択肢

| アプリごとに DbContext を持つメリット | 共通の DbContext での代わりの手段 |
|---|---|
| コマンドのタイムアウト、接続リトライをアプリごとに変える | `AddData(configureNpgsql)` で対応済み |
| 既定で追跡しない（`NoTracking`）、変更の自動検出を切る | `AddData` に `Action<DbContextOptionsBuilder>` の引数を足せば対応できる |
| インターセプター（監査ログ、`UpdatedAt` の自動設定など） | 同上 |
| API だけ DbContext をプールする（`AddDbContextPool`） | `AddData` の引数で切り替えられる |
| 接続文字列やロールを分ける | 接続文字列は既にアプリごとの設定ファイルから読んでいる |
| 使う DbSet だけを見せる | ナビゲーションでつながったエンティティはモデルに入るので、隠せる範囲は小さい |
| **アプリによってモデルを変える**（Batch だけ集計用のビューを持つ、API だけ論理削除のグローバルフィルターを付けるなど） | **共通の DbContext ではできない** |

DbContext を分けて初めて得られるのは、最後の「モデルを変える」ことだけ。

分けたときのデメリット：

- 同じ DB に 2 つのモデルができる。設定の適用漏れなどでずれると、同じテーブルが API と Batch で違う意味になり、気づきにくいバグになる
- `OrderQueries` のような共通の用語（「pending」「期限切れ」）の定義があいまいになる
- 今後マイグレーションを導入する場合、どの DbContext がマイグレーションを持つかを決める必要がある

分けるときは、エンティティと `*Configuration` は `Data` に残し、DbContext だけをアプリ側に置く。エンティティを各アプリに複製するのは避ける。

```csharp
// Data: 共通のモデル定義
public abstract class DataDbContext(DbContextOptions options) : DbContext(options)
{
    public DbSet<Order> Orders => Set<Order>();
    ...
    protected override void OnModelCreating(ModelBuilder modelBuilder) =>
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(DataDbContext).Assembly);
}

// Batch: 共通のモデルに、Batch だけのものを足す
public class BatchDbContext(DbContextOptions<BatchDbContext> options) : DataDbContext(options)
{
    public DbSet<ProductSalesView> ProductSales => Set<ProductSalesView>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        base.OnModelCreating(modelBuilder);
        modelBuilder.Entity<ProductSalesView>().HasNoKey().ToView("product_sales");
    }
}

// 登録: AddData<TContext>() にして、各アプリが自分の DbContext を渡す
builder.Services.AddData<BatchDbContext>(builder.Configuration, npgsql => npgsql.CommandTimeout(300));
```

### 採用判断

**未決定。推奨は共通の `AppDbContext` のままにすること。** アプリごとに変えたい設定は `AddData` の引数を増やして対応する。API と Batch でモデルを変えたくなったら、`Data` に基底クラスを置いてアプリ側で派生させる形で分ける。

## 6. ナビゲーションプロパティと射影

### 概要

`Order` に `Customer` と `List<OrderItem>` がナビゲーションプロパティとして定義されているが、これを定義しない場合について検討した。JOIN クエリで全項目を取得する必要はないので、専用のモデルクラスを作って SELECT の結果をマッピングするのがよいのか。モデルクラスを作ることや SQL を直接書くことの保守性の低さも懸念している。

### 現状の実装

- `Order.Customer`、`Order.Items`、`OrderItem.Order`、`OrderItem.Product` がナビゲーションプロパティ
- `Api` の `OrderRepository` は、ナビゲーションをたどってレスポンスの型（`OrderDetailResponse` など）に `Select` で射影している
- `Api` の `OrderService.CreateAsync` は `Order.Items` を使って、注文と明細を 1 回の `SaveChanges` で登録している

### 検証結果

**ナビゲーションプロパティを定義していても、全項目を取得するわけではない。** `ToQueryString()` で生成される SQL を確認した。

| 書き方 | 取得する列 |
|---|---|
| ナビゲーションを使って射影（今の書き方） | `c.name`、`p.name` などの使った列と、明細の組み立てに必要なキーだけ |
| ナビゲーションを使わず、明示的に `join` | 使った列だけ。SQL はほぼ同じ |
| `Include` | `customers` の全列（`email`、`created_at` も）を取得する |

ナビゲーションは「LINQ でたどれる関連」を定義したもので、データを読み込む指定ではない。

### 選択肢

| 方法 | メリット | デメリット |
|---|---|---|
| ナビゲーション + レスポンスの型に射影（今の書き方） | 使った列だけを取得する。コンパイル時に型チェックされ、プロパティ名の変更にも気づける。レスポンスの型を射影先に使うので、クラスが増えない | 射影の後で並べ替えると SQL に変換できないことがある（`SumShippedSalesByProductAsync` で対応済み） |
| 射影専用のクエリモデルを別に作る | — | レスポンスの型と同じ形の型が 2 つになる |
| SQL を直接書く（`Database.SqlQuery<T>` / Dapper） | ウィンドウ関数、再帰 CTE、PostgreSQL 固有の機能が使える | 列名やテーブル名の変更をコンパイル時に検出できない。`OrderQueries` などの共通の絞り込み条件を組み合わせられない。DB を使った結合テストが必要 |
| ナビゲーションを外す | ドメイン間の結合が減る（MSA の準備になる） | 下表のとおり |

ナビゲーションを外す場合の影響：

| プロパティ | 外した場合 | 判断 |
|---|---|---|
| `Order.Items` / `OrderItem.Order`（同じドメインの中） | 注文と明細を 1 回の `SaveChanges` で登録できなくなる。`o.Items.Sum(...)` などの集計も明示的な `join` / `GroupBy` で書く必要がある | 残す。注文と明細はまとめて扱う単位（集約） |
| `Order.Customer` / `OrderItem.Product`（ドメインをまたぐ） | 外部キーは `HasOne<Customer>().WithMany().HasForeignKey(o => o.CustomerId)` でナビゲーションなしでも定義できる。JOIN は明示的な `join` で書く。SQL は同じだが、コードが長くなる | 今は残す。MSA の準備として Orders から Customers への依存を消したくなったら外す |

補足：エンティティでない型に射影したクエリでは、エンティティは追跡されない。そのため `GetDetailAsync` などの `AsNoTracking()` は実際には効いていない（残しても害はない）。

### 採用判断

**未決定。推奨は、今の書き方（ナビゲーションを使ってレスポンスの型に射影）を続けること。** 読み取りで `Include` を使ったり、エンティティを丸ごと取得してからメモリー上で変換したりするのは避ける。SQL の直書きは LINQ で表せないものだけに使う。

## 7. 射影の Select が大きくなったときの対処

### 概要

エンティティやレスポンスの型が大きくなると、リポジトリの `Select` の中が大きくなり、見通しが悪くなる。対処法を検討した。

### 現状の実装

`Api` の `OrderRepository` の中に、`new OrderDetailResponse(...)` などの射影をそのまま書いている。

### 選択肢

以下の 1 と 2 は、どちらも手書きの射影とまったく同じ SQL になることを `ToQueryString()` で確認した。

#### 1. 射影の式を切り出す（ライブラリ不要）

```csharp
// Features/Orders/OrderProjections.cs（OrderContracts の隣に置く）
public static class OrderProjections
{
    public static readonly Expression<Func<OrderItem, OrderItemResponse>> Item =
        i => new OrderItemResponse(i.ProductId, i.Product.Name, i.Quantity, i.UnitPrice);

    public static readonly Expression<Func<Order, OrderDetailResponse>> Detail =
        o => new OrderDetailResponse(
            o.Id, o.CustomerId, o.Customer.Name, o.Status, o.OrderedAt, o.UpdatedAt,
            // 明細の射影も再利用できる。AsQueryable() を付けると Expression を渡せる
            o.Items.AsQueryable().OrderBy(i => i.Id).Select(Item).ToList());
}

// リポジトリ: 絞り込みだけを書く
public Task<OrderDetailResponse?> GetDetailAsync(long id, CancellationToken ct) =>
    db.Orders.Where(o => o.Id == id).Select(OrderProjections.Detail).FirstOrDefaultAsync(ct);
```

- メリット：依存が増えない。書いたとおりに動く。合計や明細の並べ替えも自由に書ける。同じ射影を複数のクエリで使い回せる
- デメリット：手で書くことは変わらない。単一のナビゲーション（`o.Customer`）から入れ子のオブジェクトを作る射影は、そのままでは再利用できない（LINQKit などが必要）

#### 2. Mapperly で自動生成する

[Mapperly](https://mapperly.riok.app/)（MIT ライセンス）はソースジェネレーターでマッピングのコードを生成し、`IQueryable` 用の射影にも対応している。

```csharp
[Mapper(RequiredMappingStrategy = RequiredMappingStrategy.Target)]
public static partial class OrderMapper
{
    public static partial IQueryable<OrderDetailResponse> ProjectToDetail(this IQueryable<Order> query);
}

// リポジトリ
db.Orders.Where(o => o.Id == id).ProjectToDetail().FirstOrDefaultAsync(ct);
```

- 4.3.1 で確認：名前の対応から `Customer.Name` を `CustomerName` に、`Product.Name` を `ProductName` に自動で入れ、明細の一覧も自動で射影した
- メリット：コードを書く量が減る。エンティティのプロパティ名を変えると、レスポンスの項目を埋められなくなってビルドエラーで気づける
- デメリット：計算した値（明細の並べ替え、`Total = Items.Sum(...)` など）は名前の対応だけでは表せない
- 注意：既定ではエンティティ側の使わない項目が警告 `RMG020` になり、`TreatWarningsAsErrors` のためエラーになる。`RequiredMappingStrategy.Target` を指定すると、レスポンスの項目を埋められないときだけエラーになる

#### 3. その他

| 方法 | 評価 |
|---|---|
| AutoMapper（`ProjectTo`） | v15（2025 年）から商用ライセンス。マッピングの誤りが実行時まで分からない。新しく導入するならおすすめしない |
| Mapster（`ProjectToType`） | 実行時にマッピングを組み立てるので、誤りの検出は Mapperly より遅い |
| DB のビューを keyless エンティティとしてマッピング | 形を整えるのは SQL に任せることになる。レポートのように形が固定されたものに限る |
| レスポンス自体を小さくする | 一覧と詳細で型を分ける（今もそうなっている）、明細などを別のエンドポイントにする。巨大なレスポンスは API 設計を見直す合図でもある |

### 採用判断

**未決定。推奨は次のとおり。**

- 今は 1（射影の式を `Features/<ドメイン>/*Projections.cs` に切り出す）。今の規模ならこれで十分で、依存も増えない
- レスポンスの型や項目が増え、名前の対応だけで埋まる単純な項目が大半になったら、2（Mapperly）に移る。1 と 2 は併用でき、自動で埋まらない計算などの項目は 1 で書く
- Batch も同じ方針にし、射影の置き場所は `Batch` の中に置く
