## 1. エラーレスポンスの形

### 概要

エラーはすべて `ErrorResponse`（`Api/Errors/ErrorResponse.cs`）の形の JSON で返す。本番と非本番で形は変わらず、スタックトレースなどの内部情報は含めない。

```json
{
  "code": "VALIDATION_ERROR",
  "message": "入力内容に誤りがあります。",
  "details": [
    { "field": "items[0].quantity", "message": "数量は1以上を指定してください。" }
  ],
  "traceId": "00-2194f81113ab8d04cc992deb4070ee4b-89724365a5b6c6ea-00"
}
```

| 項目 | 内容 |
|---|---|
| `code` | エラーの種類。クライアントはこれで処理を分ける。`ErrorDefinitions` に定義したものだけを使う |
| `message` | 利用者向けのメッセージ。既定は `ErrorDefinitions` のもので、例外ごとに上書きできる |
| `details` | 項目ごとのエラー。ないときは項目ごと省く。本文全体のエラー（JSON が壊れているなど）は `field` を省く |
| `traceId` | `Activity.Current.Id`。W3C の traceparent 形式（`00-{TraceId}-{SpanId}-{フラグ}`）で、ログのスコープに出る `TraceId` / `SpanId` と同じ値を含む（5 章） |

## 2. どのエラーで何が返るか

| 状況 | HTTP | code | 経路（3 章） |
|---|---|---|---|
| DataAnnotations の検証エラー、JSON の形式エラー、本文が空 | 400 | `VALIDATION_ERROR` | ② |
| `ValidationFailedException`（存在しない顧客 ID など、業務上の検証） | 400 | `VALIDATION_ERROR` | ① |
| `NotFoundException` | 404 | `NOT_FOUND` | ① |
| ルートに一致しない、コントローラーの `NotFound()` | 404 | `NOT_FOUND` | ③ |
| 許可されていないメソッド | 405 | `METHOD_NOT_ALLOWED` | ③ |
| 一意制約の違反（PostgreSQL の `23505`） | 409 | `CONFLICT`（「既に登録されています。」） | ① |
| `DbUpdateConcurrencyException`（楽観的同時実行制御の競合） | 409 | `CONFLICT` | ① |
| 本文が大きすぎる（`BadHttpRequestException`） | 413 | `PAYLOAD_TOO_LARGE` | ① |
| Content-Type が JSON でない | 415 | `UNSUPPORTED_MEDIA_TYPE` | ③ |
| DB に接続できない（リトライしても回復しない、一時的な Npgsql のエラー、タイムアウト） | 503 | `SERVICE_UNAVAILABLE` | ① |
| その他の想定外の例外 | 500 | `INTERNAL_SERVER_ERROR` | ① |
| クライアントが接続を切った | 499 | （本文なし） | ExceptionHandlerMiddleware |
| レスポンスを書き始めた後の例外 | （書き始めたときのステータス） | （本文が途中で切れる） | 処理できない（4 章） |

## 3. 仕組み：エラーレスポンスを作る 3 つの経路

### 概要

`Program.cs` の `AddErrorHandling()` / `UseErrorHandling()`（`Api/Errors/ErrorHandlingExtensions.cs`）で、次の 3 つを登録している。どの経路も `ErrorResponse.Create()` でレスポンスを作るので、形がそろう。

```
リクエスト
  → UseExceptionHandler   … ① 処理されなかった例外を受け取り、AppExceptionHandler で変換する
  → UseStatusCodePages    … ③ 本文のないエラー（400〜599）に本文を付ける
  → MVC（[ApiController]） … ② モデル検証エラーを 400 で返す
  → Controller → Service（ここで例外を投げる）
```

`UseErrorHandling()` はパイプラインの先頭で呼ぶ。開発環境で自動的に入る開発者向けの例外ページより先に例外を処理するので、開発環境でも本番と同じレスポンスになる。

### ① 例外：`AppExceptionHandler`

`IExceptionHandler` を実装したクラスで、`AddExceptionHandler<AppExceptionHandler>()` で登録している。`UseExceptionHandler` が例外を受け取ると、このクラスの `TryHandleAsync` が呼ばれる。

1. `Map()` が、例外の型を見て `(ErrorDefinition, message, details)` に変換する
   - `AppException`（`NotFoundException` / `ValidationFailedException`）は、例外が持っている定義・メッセージ・詳細をそのまま使う
   - EF Core や Npgsql の例外は、型（一意制約の違反は SqlState まで）を見て 409 や 503 にする
   - 上のどれにも当たらない例外は、詳細を返さずに 500 にする
2. ステータスによってログのレベルを変える

   | ステータス | レベル | 内容 |
   |---|---|---|
   | 503 | Warning | スタックトレース付き。DB 側の問題で、アプリの不具合ではないため |
   | その他の 5xx | Error | スタックトレース付き |
   | 4xx | Information | コードとメッセージだけ。クライアント側の問題のため |

3. `ErrorResponse` を JSON で書き込み、`true` を返して処理を終える

業務上のエラーは、Service が例外を投げて返す。

```csharp
?? throw new NotFoundException("注文", id);                                  // 404
throw new ValidationFailedException("customerId", $"顧客 {id} が存在しません。");   // 400 + details
```

### ② モデル検証エラー：`InvalidModelStateResponseFactory`

`[ApiController]` のコントローラーは、モデルバインディングや DataAnnotations の検証に失敗すると、アクションを呼ばずに自動で 400 を返す。既定の `ValidationProblemDetails` の代わりに `ErrorResponse` を返すように、`ApiBehaviorOptions.InvalidModelStateResponseFactory` を差し替えている。

項目名とメッセージをそろえるために、次の設定をしている。

| 設定 | 目的 |
|---|---|
| `SystemTextJsonValidationMetadataProvider` | 項目名を C# の名前（`Items`）ではなく JSON の名前（`items`）にする |
| `ToFieldName()` | JSON Path の `$.` を外す（`$.customerId` → `customerId`）。本文全体のエラー（`$`、空文字）は `field` を省く |
| `ModelBindingMessageProvider` | 既定では英語のバインディングエラーのメッセージを日本語にする |
| `AllowInputFormatterExceptionMessages = false` | JSON の読み取りエラーで .NET の型名などを返さない |
| `SuppressImplicitRequiredAttributeForNonNullableReferenceTypes = true` | JSON が壊れているときに、「The request field is required.」が重ねて出るのを防ぐ |

### ③ 本文のないエラー：`UseStatusCodePages`

ルートに一致しない 404、405、415 などは例外にならず、ステータスだけが設定されて本文は空のままになる。`UseStatusCodePages` は、400〜599 で本文がまだないレスポンスに、`ErrorDefinitions.FromStatusCode()` で引いた定義から本文を書く。定義にないステータスは `CLIENT_ERROR` / `SERVER_ERROR` になる。

- コントローラーが返す `NotFound()` なども、`SuppressMapClientErrors = true` で ProblemDetails への変換を止めているので、この経路で `ErrorResponse` になる
- ① と ② はすでに本文を書いているので、③ が重ねて本文を書くことはない

### エラーを追加するとき

- **新しい種類のエラー**：`ErrorDefinitions` に定義を足し、`AppException` を継承した例外を作る。③ でも使うなら、`ByStatusCode` の配列にも入れる
- **ライブラリの例外のレスポンスを変える**：`AppExceptionHandler.Map()` の `switch` に条件を足す

## 4. 想定外の例外の確認

### 概要

`Api/Errors/` をそのままコピーした検証用のアプリ（.NET 10）で、例外を投げるエンドポイントを呼んで動きを確認した。

### 検証結果

| No | 状況 | 結果 | 評価 |
|---|---|---|---|
| 1 | アクションで `InvalidOperationException("secret internal detail")` を投げる | 500 / `INTERNAL_SERVER_ERROR`。例外のメッセージはレスポンスに出ない。ログには Error でスタックトレース付きで 1 回だけ出る | 問題なし |
| 2 | レスポンスの `traceId` でログを探す | **ログに TraceId が出ていない**。コンソールのロガーは既定でスコープを出力しないため | 修正（5 章） |
| 3 | クライアントが接続を切る（`curl -m 1` で待機中のリクエストを中断） | 499 になるが、`AppExceptionHandler` の 499 の分岐は呼ばれない（ログが出ない） | 修正（5 章） |
| 4 | `IAsyncEnumerable` を返し、シリアライズの途中で例外を投げる | **200 で途中までの JSON** が返り、接続が切れる（curl の終了コード 18）。ログには "The response has already started, the error handler will not be executed." と出る | メモとして残す（下記） |

- 1 で二重にログが出ないのは、.NET 10 から `IExceptionHandler` が処理した例外（`TryHandleAsync` が `true` を返したもの）をフレームワークがログに出さなくなったため。.NET 8 / 9 では `ExceptionHandlerMiddleware` も Error でログを出していた
- 3 は、`ExceptionHandlerMiddleware` が `IExceptionHandler` を呼ぶ前に「`OperationCanceledException` / `IOException` かつ `RequestAborted` が立っている」かを見て、自分で 499 にするため。`AppExceptionHandler` の分岐の条件はこれに含まれるので、実行されることがなかった

### メモ：レスポンスを書き始めた後の例外（No.4）

- ステータスとヘッダーを送った後では、ステータスを 500 に変えられない。`ExceptionHandlerMiddleware` はハンドラーを呼ばずに例外を投げ直し、Kestrel が接続を切る。クライアントには 200 と途中で切れた本文が届く
- 例外のログは、`ExceptionHandlerMiddleware` と Kestrel が Error で 2 回出す
- 今の API には `IAsyncEnumerable` や `IQueryable` を返すエンドポイントがない。一覧などは `ToListAsync()` などで読み込んでから返すので、シリアライズの途中で例外が起きることはまずない
- **ストリーミングで返すエンドポイントを作るとき**（`IAsyncEnumerable`、`AsAsyncEnumerable()`、ファイルのダウンロードなど）は、この状況が起こり得る。クライアントは「200 だが JSON が壊れている」「接続が途中で切れた」をエラーとして扱う必要がある。仕組み上避けられないので、コードでは対応しない

### 補足：500 になる DB の例外

409 にしている DB の制約違反は、一意制約（`23505`）だけ。外部キー制約（`23503`）、NOT NULL 制約（`23502`）、CHECK 制約（`23514`）の違反は 500 になる。

- 例：注文の登録で、商品の存在チェックの後に別のリクエストが商品を削除すると、外部キー制約の違反で 500 になる
- アプリの不具合でも起こり得る違反なので、すべてを 4xx にするのがよいとは限らない。外部キー制約の違反だけ 409 にするかどうかは方針次第で、今回は変えていない（残課題）

## 5. 対応内容

### 変更したファイル

| ファイル | 内容 |
|---|---|
| `Api/appsettings.json` | `Logging:Console:FormatterName` を `simple`、`Logging:Console:FormatterOptions:IncludeScopes` を `true` にした（4 章 No.2） |
| `Api/Errors/AppExceptionHandler.cs` | 実行されない 499 の分岐を削除した。499 とレスポンスを書き始めた後の例外は `ExceptionHandlerMiddleware` が処理することを、クラスのコメントに書いた（4 章 No.3、No.4） |
| `README.md` | `traceId` の説明に、ログの `TraceId` / `SpanId` との対応を書いた |

### ログの出力例（対応後）

実際の API（Development、PostgreSQL に接続）で `GET /orders/999999` を呼んだときのログ。レスポンスの `traceId`（`00-2194f811...-89724365a5b6c6ea-00`）と同じ値が出る。

```
info: DotnetApiBatch.Api.Errors.AppExceptionHandler[0]
      => SpanId:89724365a5b6c6ea, TraceId:2194f81113ab8d04cc992deb4070ee4b, ParentId:0000000000000000 => ConnectionId:0HNPD6FMCRL10 => RequestPath:/orders/999999 RequestId:0HNPD6FMCRL10:00000001
      NOT_FOUND: 注文 999999 が見つかりません。
```

### 選択肢と注意点

- **設定する場所**：`appsettings.json` に書いたので、本番も開発も有効になる。コードで `AddSimpleConsole(o => o.IncludeScopes = true)` と書く方法もあるが、ログの設定は appsettings にまとまっているのでそれに合わせた
- **設定のキー**：`Logging:Console:IncludeScopes`（`ConsoleLoggerOptions.IncludeScopes`）でも動くが、非推奨（`Use ConsoleFormatterOptions.IncludeScopes instead`）。`FormatterOptions:IncludeScopes` を使う。このとき **`FormatterName` も指定する**。指定しないと非推奨の `ConsoleLoggerOptions` 側の値（既定は false）で上書きされ、スコープが出ない（実際に確認した）
- **ログが長くなる**：リクエストの中で出るすべてのログ（EF Core の SQL のログなども）に、スコープの行が 1 行増える
- **本番のログ基盤**：本番でログを JSON（`AddJsonConsole`）や OpenTelemetry で集める場合は、そちらでも TraceId が出るように設定する。OpenTelemetry なら、ログに TraceId / SpanId が自動で付く
- **Batch**：HTTP のリクエストがなく、レスポンスの `traceId` と突き合わせることもないので、変えていない

### 採用判断

**実施済み。** ビルドは警告 0・エラー 0、テストは 13 件（`Data.Tests` 5 件、`Api.Tests` 8 件）すべて成功した。

## 6. 決定事項と残課題のまとめ

### 決定事項

| 項目 | 決定内容 |
|---|---|
| エラーレスポンスの形 | `ErrorResponse`（`code` / `message` / `details` / `traceId`）。本番と非本番で同じにする |
| 業務上のエラー | Service が `AppException` を継承した例外を投げ、`AppExceptionHandler` がレスポンスに変換する |
| 想定外の例外 | 500 / `INTERNAL_SERVER_ERROR`。例外の内容は返さず、ログにだけ出す |
| ログとの突き合わせ | コンソールのログにスコープを出し、レスポンスの `traceId` と TraceId で突き合わせる |
| クライアントが接続を切った場合 | `ExceptionHandlerMiddleware` に任せる（499、本文なし） |
| レスポンスを書き始めた後の例外 | 仕組み上処理できない。コードでは対応しない（4 章のメモ） |

### 残課題

| 優先度 | 内容 | 出典 |
|---|---|---|
| 中 | API の結合テストで、例外ごとのエラーレスポンス（400 / 404 / 409 / 500 / 503）とログの TraceId を確認する。方針は [20261019_03](20261019_03_エラーレスポンスのテスト方針.md) | 4 章、20261019_01 の残課題 |
| 低 | 外部キー制約の違反（`23503`）を 409 にするか決める | 4 章の補足 |
| 低 | 本番のログ基盤（JSON / OpenTelemetry）を決めるときに、TraceId が出るように設定する | 5 章 |
| 低 | ストリーミングで返すエンドポイントを作るときに、途中で起きた例外をクライアントがどう扱うかを決める | 4 章のメモ |
| 低 | `Api` の Npgsql / EF Core の例外への依存を `Data` 側に閉じ込める | 20261018_01 の 1 章 指摘 4 |
