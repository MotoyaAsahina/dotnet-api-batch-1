## 1. 目的と範囲

### 確認すること

HTTP のリクエストから、[20261019_02 の 3 章](20261019_02_エラーレスポンスと例外処理.md#3-仕組みエラーレスポンスを作る-3-つの経路)の 3 つの経路を通って、次のようになることを確認する。

| 観点 | 内容 |
|---|---|
| レスポンス | ステータス、`code`、`message`、`details`（有無と `field`）、`traceId` の形式、Content-Type が `application/json` |
| 内部情報 | 例外のメッセージやスタックトレースが、レスポンスに出ない |
| ログ | ステータスに応じたレベル（Error / Warning / Information）で出る。5xx は例外（スタックトレース）付きで出る。スコープの `TraceId` が、レスポンスの `traceId` と一致する |

### 確認しないこと

| 内容 | 理由 |
|---|---|
| 業務ロジック（どの条件で `NotFoundException` を投げるか、など） | `OrderServiceTests`（単体テスト）で確認している |
| クライアントが接続を切ったとき（499） | `ExceptionHandlerMiddleware`（フレームワーク）の動き。アプリのコードがない |
| レスポンスを書き始めた後の例外 | 仕組み上処理できない（20261019_02 の 4 章のメモ） |
| コンソールのログの書式（スコープが出力されるか） | `appsettings.json` の設定で決まる。テストではスコープに `TraceId` が入っていることまでを確認し、出力は手で確認した（20261019_02 の 5 章） |

## 2. テストの分け方

### 概要

**DB を使わないテスト（A）を中心にする。** DB を使うテスト（B）は、本物のリポジトリを通る数本にとどめる。

| | A：DB なし | B：DB あり |
|---|---|---|
| サーバー | `WebApplicationFactory<Program>`（TestServer） | 同じ |
| リポジトリ | NSubstitute のモックに差し替え、例外を投げさせる | 本物。DB は Testcontainers.PostgreSql |
| 対象 | 3 つの経路すべて。例外の種類ごとの変換（`Map()` のすべての分岐） | 本物の DB で起きる 404 / 400 |
| 速さ | 1 件あたり数十 ms | コンテナの起動に約 6 秒（クラスで共有） |
| Docker | 不要 | 必要 |

### A を中心にする理由

409 / 500 / 503 は、今の API では本物の DB を使っても起こせない、または起こすのに手間がかかる。

| エラー | 本物の DB で起こせるか |
|---|---|
| 409（一意制約の違反） | 一意制約は `customers.email` だけで、顧客を登録するエンドポイントがない |
| 500（想定外の例外） | 不具合がないと起きない |
| 503（DB に接続できない） | DB を止めると起こせるが、`EnableRetryOnFailure` の既定の設定でリトライするので、レスポンスが返るまで時間がかかる |

リポジトリに例外を投げさせれば、どれも数十 ms で確認できる。リポジトリの差し替えは [20261019_01](20261019_01_単体テストのしやすさ.md) でインターフェースにしたので、`ConfigureTestServices` で入れ替えるだけで済む。

### B の位置づけ

B は、本物のリポジトリと DB を通しても A と同じレスポンスになるかを確認するもの。正常系も含めた API の結合テスト（[20261019_01 の 4 章](20261019_01_単体テストのしやすさ.md#4-推奨するテストの構成) No.3）と同じ仕組み（フィクスチャー）を使うので、そちらと合わせて作る。

## 3. テストケース

### A：DB なし

すべてのケースで共通して、Content-Type が `application/json` であること、`traceId` が `00-{32 桁}-{16 桁}-{2 桁}` の形式であることを確認する。

| No | 経路 | 起こし方 | ステータス / code | 個別に確認すること |
|---|---|---|---|---|
| A1 | ① | `GET /orders/1` で、リポジトリが `InvalidOperationException("内部の情報")` を投げる | 500 / `INTERNAL_SERVER_ERROR` | レスポンスに「内部の情報」が出ない。ログは Error、例外付き、`TraceId` がレスポンスと一致する |
| A2 | ① | リポジトリが `DbUpdateException`（内側が `PostgresException`、SqlState `23505`）を投げる | 409 / `CONFLICT` | `message` が「既に登録されています。」。ログは Information |
| A3 | ① | リポジトリが `DbUpdateConcurrencyException` を投げる | 409 / `CONFLICT` | `message` が既定のもの |
| A4 | ① | リポジトリが外部キー制約の違反（SqlState `23503`）を投げる | 500 / `INTERNAL_SERVER_ERROR` | 今の方針を固定するテスト。409 にすると決めたら変える（20261019_02 の残課題） |
| A5 | ① | リポジトリが `RetryLimitExceededException` / `NpgsqlException`（内側が `TimeoutException`）/ `TimeoutException` を投げる（`[Theory]`） | 503 / `SERVICE_UNAVAILABLE` | ログは Warning、例外付き |
| A6 | ① | リポジトリが `BadHttpRequestException("…", 413)` を投げる | 413 / `PAYLOAD_TOO_LARGE` | 本文のサイズの上限は TestServer では効かないので、例外で代用する（7 章 No.4） |
| A7 | ① | `GET /orders/1` で、リポジトリが `null` を返す | 404 / `NOT_FOUND` | `message` が「注文 1 が見つかりません。」。ログは Information、例外なし |
| A8 | ① | `POST /orders` で、顧客のリポジトリが `ExistsAsync` に `false` を返す | 400 / `VALIDATION_ERROR` | `details` が `[{ field: "customerId", … }]` |
| A9 | ② | `POST /orders` で `quantity: 0` | 400 / `VALIDATION_ERROR` | `details[0].field` が `items[0].quantity` |
| A10 | ② | `POST /orders` で壊れた JSON（`{bad`） | 400 / `VALIDATION_ERROR` | `details` に `field` がない |
| A11 | ② | `POST /orders` で本文が空 | 400 / `VALIDATION_ERROR` | |
| A12 | ③ | `GET /nope` | 404 / `NOT_FOUND` | `message` が既定のもの |
| A13 | ③ | `GET /customers/abc/orders`（ルート制約に一致しない） | 404 / `NOT_FOUND` | |
| A14 | ③ | `DELETE /orders/1` | 405 / `METHOD_NOT_ALLOWED` | |
| A15 | ③ | `POST /orders` を `text/plain` で送る | 415 / `UNSUPPORTED_MEDIA_TYPE` | |

- A1〜A6 は `Map()` の分岐ごとに 1 件以上ある。`Map()` に分岐を足したら、A にもケースを足す
- A7・A8 はサービスを通して `AppException` を起こすので、`AppException` からレスポンスへの変換を確認できる

### B：DB あり

| No | リクエスト | ステータス / code | 個別に確認すること |
|---|---|---|---|
| B1 | `GET /orders/999999` | 404 / `NOT_FOUND` | |
| B2 | `GET /customers/999999/orders` | 404 / `NOT_FOUND` | `message` が「顧客 999999 が見つかりません。」 |
| B3 | `POST /orders`（存在しない顧客） | 400 / `VALIDATION_ERROR` | `details` が `customerId` |
| B4 | `POST /orders`（存在しない商品） | 400 / `VALIDATION_ERROR` | `details` が `items` |

- 初期データ（`db/init/02_data.sql`）を変更しないリクエストだけにしている。データを書き込むテストを足すときは、テストごとにデータを戻す仕組み（Respawn など）を検討する（残課題）

## 4. レスポンスとログの検証方法

### レスポンス：JSON のまま確認する

- `ReadFromJsonAsync<ErrorResponse>()` で API の型に読み込むと、項目名が変わっても型と一緒に変わるので、テストが失敗しない。`JsonDocument`（`JsonElement`）で読み、`"code"` `"traceId"` などの名前で確認する
- `details` がないケースは、項目そのものがない（`TryGetProperty` が `false`）ことを確認する。`null` が出力されていないことも確かめられる
- 内部情報が出ないことは、レスポンスの本文全体に例外のメッセージが含まれないことで確認する

### ログ：FakeLogger で集める

- `Microsoft.Extensions.Diagnostics.Testing` の `AddFakeLogging()` を `ConfigureTestServices` で呼ぶと、ログが `FakeLogCollector` に集まる
- カテゴリが `AppExceptionHandler` のログを取り出し、`Level` と `Exception` を確認する
- `FakeLogRecord.Scopes` に、ASP.NET Core が付けるスコープ（`SpanId` / `TraceId` / `ParentId`）が入る。`TraceId` の値が、レスポンスの `traceId` の 2 番目の要素（`00-{TraceId}-{SpanId}-{フラグ}`）と一致することを確認する

## 5. プロジェクトの構成

### 推奨：`tests/DotnetApiBatch.Api.IntegrationTests` を新しく作る

```
tests/
├── DotnetApiBatch.Api.Tests/              単体テスト（既存）。Service をモックで確認する
└── DotnetApiBatch.Api.IntegrationTests/   HTTP からのテスト（新規）
    ├── Infrastructure/
    │   ├── ApiFactory.cs                  A 用。リポジトリをモックに、ログを FakeLogger にする
    │   ├── PostgresFixture.cs             B 用。PostgreSQL のコンテナ（コレクションで共有）
    │   └── ErrorResponseAssert.cs         レスポンスの共通の確認（Content-Type、traceId の形式）
    └── Errors/
        ├── ExceptionMappingTests.cs       A1〜A8
        ├── RequestErrorTests.cs           A9〜A15
        └── DbErrorTests.cs                B1〜B4
```

| 選択肢 | メリット | デメリット |
|---|---|---|
| **新しいプロジェクト（推奨）** | 単体テストと結合テストの区別が、プロジェクトでわかる。Docker を使うテストと Testcontainers の依存を、単体テストから切り離せる | プロジェクトが 1 つ増える |
| 既存の `Api.Tests` に入れる | プロジェクトが増えない | Docker がない環境で `Api.Tests` を実行すると、B が失敗する。単体テストだけを実行したいときにフィルターが要る |

- A は Docker なしで動く。Docker のない環境で A だけを実行するときは、B に `[Trait("Category", "Db")]` を付けて `dotnet test --filter "Category!=Db"` で除く

### 追加するパッケージ

| パッケージ | バージョン | `Directory.Packages.props` のグループ |
|---|---|---|
| `Microsoft.AspNetCore.Mvc.Testing` | 10.0.13 | Microsoft.Extensions / ASP.NET Core（ランタイムにそろえる） |
| `Microsoft.Extensions.Diagnostics.Testing` | 10.11.0 | テスト（`TimeProvider.Testing` と同じく dotnet/extensions のリリースで上がる） |
| `Testcontainers.PostgreSql` | 4.7.0 | テスト |

NSubstitute、xunit（2.x）などは既存のものを使う。

### `ApiFactory`（A）の設定

| 設定 | 理由 |
|---|---|
| `UseEnvironment("Production")` | 本番と同じ動きを確認する。`appsettings.Development.json` の接続文字列（localhost）も読まなくなる |
| `UseSetting("ConnectionStrings:AppDb", "Host=nowhere.invalid")` | `AddData()` は起動時に接続文字列がないと例外を投げるので、ダミーを渡す。`Program` で `builder.Configuration` から読む前に反映されることを確認した |
| 3 つのリポジトリをモックに差し替える | DB に接続しないようにする。差し替え漏れがあると、存在しないホストへの接続でリトライが始まり、テストが遅くなる |
| `AddFakeLogging()` | ログを検証する |
| テストごとに `ApiFactory` を作る | モックの設定がテストの間で混ざらないようにする。作り直しても 1 件あたり数十 ms |

- .NET 10 では、トップレベルステートメントの `Program` が自動で public になる（`typeof(Program).IsPublic` が `true`）。`public partial class Program;` を書く必要はない
- テストのログに `Failed to determine the https port for redirect.`（`UseHttpsRedirection`）の Warning が出るが、テストには影響しない

### `PostgresFixture`（B）の設定

- イメージは `compose.yaml` と同じ `postgres:18.3-alpine` にする
- `db/init` を `/docker-entrypoint-initdb.d/` にコピー（`WithResourceMapping`）すると、スキーマと初期データがそのまま使える。`db/init` のパスは、テストの実行ディレクトリから `DotnetApiBatch.slnx` のあるディレクトリまでさかのぼって求める
- コンテナは `ICollectionFixture` で、B のテストクラス全体で 1 つにする
- 接続文字列は `UseSetting("ConnectionStrings:AppDb", container.GetConnectionString())` で渡す

## 6. 実装例

試作したコードを整理したもの。

### `ApiFactory`

```csharp
public class ApiFactory : WebApplicationFactory<Program>
{
    public ICustomerRepository Customers { get; } = Substitute.For<ICustomerRepository>();
    public IProductRepository Products { get; } = Substitute.For<IProductRepository>();
    public IOrderRepository Orders { get; } = Substitute.For<IOrderRepository>();

    public FakeLogCollector Logs => Services.GetFakeLogCollector();

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseEnvironment("Production");
        builder.UseSetting("ConnectionStrings:AppDb", "Host=nowhere.invalid");
        builder.ConfigureTestServices(services =>
        {
            services.RemoveAll<ICustomerRepository>().AddSingleton(Customers);
            services.RemoveAll<IProductRepository>().AddSingleton(Products);
            services.RemoveAll<IOrderRepository>().AddSingleton(Orders);
            services.AddFakeLogging();
        });
    }
}
```

### A1：想定外の例外

```csharp
[Fact]
public async Task Unexpected_exception_returns_500_without_internal_details()
{
    using var factory = new ApiFactory();
    factory.Orders.GetDetailAsync(1, Arg.Any<CancellationToken>())
        .Returns<OrderDetailResponse?>(_ => throw new InvalidOperationException("内部の情報"));

    var response = await factory.CreateClient().GetAsync("/orders/1");

    Assert.Equal(HttpStatusCode.InternalServerError, response.StatusCode);
    var body = await ErrorResponseAssert.ReadAsync(response);   // Content-Type と traceId の形式も確認する
    Assert.Equal("INTERNAL_SERVER_ERROR", body.GetProperty("code").GetString());
    Assert.DoesNotContain("内部の情報", body.GetRawText());

    var log = factory.Logs.GetSnapshot().Single(r => r.Category == typeof(AppExceptionHandler).FullName);
    Assert.Equal(LogLevel.Error, log.Level);
    Assert.IsType<InvalidOperationException>(log.Exception);
    Assert.Equal(ErrorResponseAssert.TraceIdOf(body), ErrorResponseAssert.TraceIdOf(log));
}
```

- `TraceIdOf(JsonElement)` は `traceId` を `-` で分けた 2 番目の要素を、`TraceIdOf(FakeLogRecord)` は `Scopes` の中のキー `TraceId` の値を返す

### A2：一意制約の違反

```csharp
var exception = new DbUpdateException(
    "保存に失敗しました",
    new PostgresException("duplicate key", "ERROR", "ERROR", PostgresErrorCodes.UniqueViolation));
```

- `PostgresException` は public のコンストラクターで作れる。外部キー制約の違反（A4）は `PostgresErrorCodes.ForeignKeyViolation` を使う

### `PostgresFixture`

```csharp
public class PostgresFixture : IAsyncLifetime
{
    public PostgreSqlContainer Container { get; } = new PostgreSqlBuilder()
        .WithImage("postgres:18.3-alpine")
        .WithDatabase("app").WithUsername("app").WithPassword("app")
        .WithResourceMapping(new DirectoryInfo(Path.Combine(RepositoryRoot.Path, "db", "init")), "/docker-entrypoint-initdb.d/")
        .Build();

    public Task InitializeAsync() => Container.StartAsync();
    public Task DisposeAsync() => Container.DisposeAsync().AsTask();

    public WebApplicationFactory<Program> CreateFactory() =>
        new WebApplicationFactory<Program>().WithWebHostBuilder(builder =>
            builder.UseSetting("ConnectionStrings:AppDb", Container.GetConnectionString()));
}
```

## 7. 試作で確認したこと

スクラッチのテストプロジェクトで、本体の `DotnetApiBatch.Api` を参照し、.NET 10・xunit 2.9.3 で確認した。

| No | 確認したこと | 結果 |
|---|---|---|
| 1 | `WebApplicationFactory<Program>` を、`public partial class Program;` なしで使えるか | 使える。`typeof(Program).IsPublic` が `true` |
| 2 | `UseSetting` の接続文字列が、`Program` で `AddData()` が読むより前に反映されるか | 反映される。Production・`Host=nowhere.invalid` で起動した |
| 3 | リポジトリのモックに例外を投げさせて、500 / 409 / 503 になるか | なる。1 件あたり 25〜60 ms |
| 4 | 本文のサイズの上限（413）を TestServer で確認できるか | **できない**。31MB の本文がそのまま受け付けられ、検証エラーの 400 になった |
| 5 | 本物の Kestrel（`UseKestrel()`）なら 413 を確認できるか | 既定の上限（約 30MB）を超える本文では、送信中に Kestrel が接続を閉じ、クライアントが Broken pipe になった。上限を 1KB にして 4KB を送ると 413 になった。ただし Kestrel の設定を変える必要があり、ポートも 5000 に固定されたので、A では例外で代用する |
| 6 | `FakeLogRecord.Scopes` に `TraceId` が入り、レスポンスと一致するか | 一致する |
| 7 | ② ③（検証エラー、壊れた JSON、404、405、415）が DB なしで確認できるか | できる |
| 8 | Testcontainers（`postgres:18.3-alpine`、`db/init` をコピー）で B が動くか | 動く。コンテナの起動に約 6 秒、3 リクエストで約 0.9 秒 |

### 試作で見つかった、前回の設定の問題

20261019_02 で `appsettings.json` に追加した `Logging:Console:IncludeScopes` は、非推奨の `ConsoleLoggerOptions.IncludeScopes` だった。`FormatterName: "simple"` と `FormatterOptions:IncludeScopes: true` に直し、ログにスコープが出ることを実際の API で確認した。`FormatterName` を書かないと、非推奨の側の値（false）で上書きされてスコープが出ない（20261019_02 の 5 章にも追記した）。

## 8. 決定事項と残課題のまとめ

### 推奨（未実装）

| 項目 | 内容 |
|---|---|
| テストの中心 | DB なし（TestServer + リポジトリのモック）。`Map()` の分岐ごとにケースを用意する |
| DB ありのテスト | 本物のリポジトリを通る 404 / 400 の数本。正常系の結合テストとフィクスチャーを共有する |
| プロジェクト | `tests/DotnetApiBatch.Api.IntegrationTests` を新しく作る |
| レスポンスの確認 | API の型に読み込まず、JSON の項目名で確認する |
| ログの確認 | FakeLogger でレベル・例外・スコープの `TraceId` を確認する |
| 413 | 例外（`BadHttpRequestException`）で代用し、Kestrel の上限そのものはテストしない |

### 残課題

| 優先度 | 内容 | 出典 |
|---|---|---|
| 中 | この方針で A / B を実装する。`DotnetApiBatch.slnx` と README のテストの説明も更新する | 本ノート |
| 中 | CI で Docker を使えるようにする（B と、Repository の結合テストに必要） | 5 章、20261019_01 の残課題 |
| 低 | データを書き込む結合テストを足すときに、テストごとにデータを戻す仕組み（Respawn、トランザクションのロールバックなど）を決める | 3 章 B |
| 低 | 外部キー制約の違反を 409 にすると決めたら、A4 を変える | 3 章 A4、20261019_02 の残課題 |
