## 1. 現状の評価

### 概要

対応前の API は、**Service の単体テストがしにくい形**だった。

### 現状の実装（対応前）

**できていること**

- 依存はすべてコンストラクターで受け取っている（プライマリコンストラクター）
- 時刻は `TimeProvider` で受け取っているので、テストでは `FakeTimeProvider`（`Microsoft.Extensions.TimeProvider.Testing`）に差し替えられる
- コントローラーは薄く、業務エラーは例外にして `AppExceptionHandler` でまとめてレスポンスに変換している

**できていないこと**

- `OrderService` が受け取る `CustomerRepository` / `ProductRepository` / `OrderRepository` は具象クラスで、メソッドも virtual ではない。そのため、モックに差し替えられない
- 結果として `OrderService.CreateAsync` をテストするには、本物の `AppDbContext`、つまり DB が必要だった。このメソッドには顧客の存在確認、存在しない商品の検出、注文時点の単価の保存、日時の設定など、一番テストしたいロジックが詰まっている

## 2. Java との違い：C# ではインターフェースが Java よりも必要

| | Java (Mockito) | C# (Moq / NSubstitute) |
|---|---|---|
| メソッドのデフォルト | virtual（オーバーライド可） | **非 virtual** |
| 具象クラスのモック | できる（final でも inline mock maker で可） | **virtual メンバーしか差し替えられない** |

- Java では「インターフェースにしておくとモックしやすい」程度の話だが、C# では **インターフェースか virtual にしないと、そもそもモックできない**
- 慣習としてはインターフェースを使う。メソッドを全部 virtual にするやり方はほとんど見かけない

---

## 3. どこをインターフェースにするか

### Repository（DB との境界）：する

- `ICustomerRepository` / `IProductRepository` / `IOrderRepository` を作り、`AddScoped<IOrderRepository, OrderRepository>()` で登録する
- EF Core の公式ドキュメントも、DB なしでテストするなら Repository を差し替える方法を推奨している。`DbContext` 自体をモックする方法や、InMemory プロバイダーは推奨されていない
- 前回のレビュー（[20261018_01 の 4 章](20261018_01_アーキテクチャ・実装レビュー.md#4-モジュラーモノリスでのドメイン間の-join)）にある `ICustomerLookup` / `IProductCatalog`（他モジュールの公開インターフェース）とも方向が同じ。`OrderService` が他ドメインのインターフェースに依存する形にすれば、テストしやすさとモジュールの境界づくりを一度に進められる

### Service：基本しない

- コントローラーは Service を呼ぶだけなので、Service をモックにしてコントローラーを単体テストしてもあまり意味がない
- コントローラー側で確かめたいのは、ルーティング、enum の snake_case 変換、DataAnnotations による 400、例外からエラーレスポンスへの変換など。これらは `WebApplicationFactory<Program>` を使った結合テストのほうが確実に確認できる
- `ProductService` のように Repository を呼ぶだけの Service は、テストの対象にもなりにくい
- 「.NET では全部 `IXxxService` にする」という現場も多いが、それはテストのためというより慣習

## 4. 推奨するテストの構成

| No | 種類 | 対象 | 方法 |
|---|---|---|---|
| 1 | 単体テスト | Service | Repository をインターフェースにして NSubstitute でモックし、`FakeTimeProvider` と組み合わせて業務ロジックを確認する |
| 2 | 結合テスト | Repository | Testcontainers.PostgreSql で本物の PostgreSQL に対して実行する。`db/init` のスキーマと初期データをそのまま使える |
| 3 | 結合テスト | API（HTTP から） | `WebApplicationFactory` と Testcontainers で、一連の動きを数本確認する |

- Batch の `ExecuteUpdateAsync` は InMemory プロバイダーでは動かない。射影や `Sum` の SQL への変換も PostgreSQL でしか正しく確認できないので、Repository はモックしないで 2 で確認する
- Batch の `CancelExpiredOrdersJob` は、ロジックがしきい値の計算くらいしかない。2 の結合テストで十分で、モックはなくてもよい

## 5. 対応内容

### 概要

API だけを対象に、4 章の 1（Service の単体テスト）を実施した。Batch と 2・3 は未対応。

### 変更したファイル

| ファイル | 内容 |
|---|---|
| `Api/Features/*/*Repository.cs` | `ICustomerRepository` / `IProductRepository` / `IOrderRepository` を追加し、既存のクラスに実装させた。XML コメントはインターフェースに移した |
| `Api/Features/Orders/OrderService.cs`、`Api/Features/Catalog/ProductService.cs` | コンストラクターの引数をインターフェースに変えた |
| `Api/Program.cs` | `AddScoped<I*Repository, *Repository>()` で登録するようにした |
| `tests/DotnetApiBatch.Api.Tests`（新規） | `OrderService` の単体テスト（8 件） |
| `Directory.Packages.props` | `NSubstitute` 6.2.0、`NSubstitute.Analyzers.CSharp` 1.0.17、`Microsoft.Extensions.TimeProvider.Testing` 10.11.0 を追加 |
| `DotnetApiBatch.slnx` | `Api.Tests` を追加 |
| `README.md` | テストの方針、リポジトリのインターフェース、プロジェクト構成を追記 |

### 追加したテスト（`OrderServiceTests`）

| メソッド | 確認すること |
|---|---|
| `GetDetailAsync` | 見つかればリポジトリの結果をそのまま返す |
| | 見つからなければ `NotFoundException` |
| `ListByCustomerAsync` | `status` をリポジトリに渡し、結果をそのまま返す |
| | 顧客がいなければ `NotFoundException`。注文は検索しない |
| `CreateAsync` | `pending`・現在時刻・注文時点の単価で注文を作り、`Add` → `SaveChangesAsync` の順に呼ぶ。保存時に採番された ID を返す |
| | 同じ商品を複数の明細で注文しても、商品の検索は ID を重複させずに 1 回だけ |
| | 顧客がいなければ `customerId` の `ValidationFailedException`。保存しない |
| | 存在しない商品をまとめて `items` の `ValidationFailedException` で返す。保存しない |

- `OrderService` の処理（重複の除去、単価、ステータス）をわざと壊すとテストが失敗することを確認した
- `ProductService` はリポジトリを呼ぶだけなので、テストは書いていない

### 選択肢と注意点

- **インターフェースの置き場所**：実装と同じファイルに置いた。このリポジトリでは関連する型を 1 ファイルにまとめている（`OrderContracts.cs`、`AppExceptions.cs` など）ので、それに合わせた。1 型 1 ファイルにそろえる場合は、`I*Repository.cs` に分ける
- **モックのライブラリ**：NSubstitute を選んだ。Moq は 2023 年に、ビルド時に開発者のメールアドレスを収集する SponsorLink を同梱して問題になった（その後削除）。NSubstitute は書き方が短く、Analyzer で誤用（virtual でないメンバーのモックなど）をビルド時に検出できる
- **xUnit のバージョン**：`Data.Tests` に合わせて xunit 2.x にした。`xunit.v3` への移行は前回の残課題（1 章 指摘 6）で、両方のテストプロジェクトをまとめて移す
- **`dotnet add package` の副作用**：`Directory.Packages.props` の空行を消し、追加する場所も選べない。追加後に手で整えた
- **`Microsoft.Extensions.TimeProvider.Testing` のバージョン**：dotnet/extensions のリリースに合わせて上がる（10.11.0）ので、ランタイムにそろえる `Microsoft.Extensions.*` のグループではなく、テストのグループに置いた

### 採用判断

**実施済み。** ブランチ `feature/api-service-unit-tests` で PR を作成した。ビルドは警告 0・エラー 0、テストは 13 件（`Data.Tests` 5 件、`Api.Tests` 8 件）すべて成功。

## 6. 決定事項と残課題のまとめ

### 決定事項

| 項目 | 決定内容 |
|---|---|
| Repository | インターフェース（`I*Repository`）を定義し、サービスはインターフェースに依存する |
| Service | インターフェースにしない |
| モックのライブラリ | NSubstitute（Analyzer も入れる） |
| 時刻 | `TimeProvider` を受け取り、テストでは `FakeTimeProvider` を使う |

### 残課題

| 優先度 | 内容 | 出典 |

| 中 | 依存ルールのテストに「サービスはリポジトリの具象クラスに依存しない」を加える | 3 章、20261018_01 の残課題 |
