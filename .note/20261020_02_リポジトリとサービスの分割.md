## 1. 現状：Features の構成

### 概要

`Api/Features/<ドメイン>/` の下に、Contracts / Repository / Service が 1 ファイルずつある。リポジトリのインターフェースと実装は同じファイルにある。

| ドメイン | ファイル |
|---|---|
| Catalog | `ProductContracts.cs`、`ProductRepository.cs`、`ProductService.cs` |
| Customers | `CustomerRepository.cs`（サービスはない） |
| Orders | `OrderContracts.cs`、`OrderRepository.cs`、`OrderService.cs` |

DI の登録は `Api/Program.cs` にドメインごとにコメントを付けて並べている。

## 2. 分けどきの目安

### 概要

**行数ではなく、1 つのクラスに関係のない責務が同居しているかで判断する。** 今の Orders に、すでに兆候が出ている。

### 今のコードに出ている兆候

| 兆候 | 場所 | 内容 |
|---|---|---|
| メソッドが使わない依存が多い | `OrderService` | コンストラクターで 5 つ（customers、products、orders、unitOfWork、timeProvider）受け取るが、`GetDetailAsync` が使うのは `orders` だけ。その結果、`OrderServiceTests` はどのテストでも 5 つすべてのモックを用意している |
| 読み取りと書き込みが同居している | `IOrderRepository` | レスポンスの形に射影する `AsNoTracking` の読み取り（`GetDetailAsync`、`ListByCustomerAsync`）と、エンティティを登録する書き込み（`Add`）が同じインターフェースにある |

## 3. 改善の選択肢

軽い順に並べる。

### A. リポジトリを読み取りと書き込みで分ける

最初に分けるならここが一番自然。

```
Features/Orders/
  IOrderReadRepository.cs / OrderReadRepository.cs  … GetDetail, ListByCustomer（射影・AsNoTracking）
  IOrderRepository.cs / OrderRepository.cs          … Add, 更新用の Get（追跡あり）
```

- 読み取りは画面の数だけ増えるが、書き込みはあまり増えない。分けておくと、増える側だけが大きくなる
- `OrderQueries` という名前は `Data/Orders/OrderQueries.cs`（共通の絞り込み条件）と重なるので、読み取り側は `OrderReadRepository` などで区別する

### B. サービスをユースケースごとに分ける（Vertical Slice）

フォルダ名がすでに `Features` なので、縦割りに寄せるのが素直。

```
Features/Orders/
  CreateOrder/
    CreateOrderRequest.cs      … OrderContracts.cs から移す
    CreateOrderResponse.cs
    CreateOrderHandler.cs      … customers, products, orders, unitOfWork, timeProvider
  GetOrderDetail/
    OrderDetailResponse.cs
    GetOrderDetailHandler.cs   … 読み取りリポジトリだけ
  ListCustomerOrders/
    ...
  Shared/                      … 複数のユースケースで使う型（あれば）
```

- 各ハンドラーが受け取る依存は、自分が使うものだけになる。テストも、そのユースケースに必要なモックだけで書ける
- 機能を足すと、既存ファイルを編集する代わりにフォルダが 1 つ増える。変更がぶつかりにくい
- `OrderContracts.cs` のリクエスト・レスポンスも、使うユースケースの隣に移せる
- MediatR などのライブラリは不要。普通のクラスを DI に登録し、コントローラーに注入すれば十分

### C. 条件の組み合わせでリポジトリのメソッドが増えるのを抑える

`ListByCustomerAndStatus…`、`ListByCustomerAndDateRange…` のように、条件の組み合わせごとにメソッドを足していくとすぐに破綻する。

- 絞り込み条件は、既存の `OrderQueries` の拡張メソッド（`WithStatus`、`OrderedBefore`）に追加して部品にする
- 一覧の検索は、`OrderSearchCriteria` のような条件オブジェクトを 1 つ受け取るメソッドにまとめる
- 条件の値が null でないときだけ絞り込む書き方は 20261020_02 にまとめた

### D. 業務ルールをエンティティに寄せる

`OrderService.CreateAsync` は、`Order` の組み立て（初期状態、注文時点の単価の記録）をサービスの中で行っている。キャンセルや発送など状態遷移が増えるなら、`Order.Create(...)` や `order.Cancel(now)` に寄せるとサービスが薄くなる。

- 注意：エンティティは `Data` にあり、Batch と共有している。Batch の `CancelPendingOrderedBeforeAsync` は `ExecuteUpdateAsync` でエンティティを通らずに更新するので、ルールが 2 か所に分かれる。どこまでエンティティに寄せるかは、別途決めて記録に残す

## 4. 付随する整理

| 項目 | 内容 |
|---|---|
| DI の登録 | クラスが増えると `Program.cs` が長くなる。`AddOrdersFeature()` のように、ドメインごとに登録をまとめる拡張メソッドを作る |
| インターフェースと実装のファイル | 別ファイルにするのは手軽で効果がある。ただし責務の分割の代わりにはならない |
| `partial class` でファイルだけ分ける | おすすめしない。見た目が短くなるだけで、依存の多さやテストのしにくさは変わらない |
| 依存ルールのテスト | 縦割りにしたら、`ArchitectureTests` に「ユースケースのフォルダ同士は互いに依存しない」を足すと、構成が崩れにくい |

## 5. 方針と残課題のまとめ

### 方針（案）

| 段階 | きっかけ | 対応 |
|---|---|---|
| 1 | 今の規模 | A：リポジトリを読み取りと書き込みで分ける |
| 2 | Orders のユースケースが 4〜5 個を超えたら | B：ユースケースごとに分ける |
| 3 | 状態遷移が増えてきたら | D：業務ルールをエンティティに寄せる |

どれも未実施。

### 残課題

| 優先度 | 内容 | 出典 |
|---|---|---|
| 低 | Orders のリポジトリを読み取りと書き込みで分けるか決める | 3 章の A |
| 低 | ユースケースごとに分けるときの、フォルダ・クラスの命名（`Handler` など）と DI 登録の方法を決める | 3 章の B、4 章 |
| 低 | 業務ルールをエンティティに寄せる範囲と、Batch の `ExecuteUpdateAsync` との分担を決める | 3 章の D |
