# 条件付きのクエリ（2026-10-20）

クエリに使う条件の値が null でないときだけ絞り込む、といった「特定の条件のときだけクエリメソッドを使う」書き方を整理した記録です。拡張メソッドと呼び出し例は、スクラッチのプロジェクトでコンパイルが通ることを確認しました。リポジトリのコードは変更していません。

## 1. 現状

## 2. 書き方の選択肢

### A. `if` で `IQueryable` を再代入する（今の書き方）

```csharp
var query = db.Orders.AsNoTracking().Where(o => o.CustomerId == customerId);
if (status is { } s)
{
    query = query.WithStatus(s);
}
if (from is { } f)
{
    query = query.OrderedAfter(f);
}
return await query.OrderByDescending(o => o.OrderedAt).Select(...).ToListAsync(ct);
```

- 一番読みやすく、追加の仕組みもいらない。条件が 2〜3 個ならこれで十分
- `IQueryable` は遅延実行なので、`if` で `Where` を積んでも SQL は最後の `ToListAsync` で 1 回だけ発行される
- `query` の型は `IQueryable<Order>` にしておく。先に `OrderBy` を付けると `IOrderedQueryable` になり、再代入しにくい。並べ替えは絞り込みの後にする

### B. `WhereIf` / `ApplyIfNotNull` の拡張メソッドでメソッドチェーンにする

条件が増えて `if` が並ぶようになったら使う。ドメインに依存しない汎用の拡張なので、置くなら `Data` の直下（例：`Data/QueryableExtensions.cs`）。

```csharp
public static class QueryableExtensions
{
    /// <summary>condition が true のときだけ絞り込む。</summary>
    public static IQueryable<T> WhereIf<T>(
        this IQueryable<T> query, bool condition, Expression<Func<T, bool>> predicate) =>
        condition ? query.Where(predicate) : query;

    /// <summary>value が null でないときだけ、その値でクエリメソッドを適用する。</summary>
    public static IQueryable<T> ApplyIfNotNull<T, TValue>(
        this IQueryable<T> query, TValue? value, Func<IQueryable<T>, TValue, IQueryable<T>> apply)
        where TValue : struct =>
        value is { } v ? apply(query, v) : query;
}
```

呼び出し側：

```csharp
var query = db.Orders.AsNoTracking()
    .Where(o => o.CustomerId == customerId)
    // OrderQueries のメソッドをメソッドグループのまま渡せる
    .ApplyIfNotNull(status, OrderQueries.WithStatus)
    .ApplyIfNotNull(from, OrderQueries.OrderedAfter)
    // その場限りの条件は WhereIf で書く
    .WhereIf(!string.IsNullOrWhiteSpace(keyword), o => o.Customer.Name.Contains(keyword!))
    .WhereIf(productIds is { Count: > 0 }, o => o.Items.Any(i => productIds!.Contains(i.ProductId)));
```

- `ApplyIfNotNull` は null でない値を渡すので、`OrderQueries` の既存メソッドを null 非許容のまま使い回せる
- `WhereIf` の式の中ではコンパイラーに null チェックが伝わらないので、`keyword!` のように `!` が必要。`condition` が false のときは式が SQL に変換されないので、実行時には問題ない
- `.ApplyIf(status is { } s, q => q.WithStatus(s))` のように、パターンで受けた変数を同じ呼び出しのラムダで使うと、未割り当ての変数としてコンパイルエラーになる。null 許容の値が条件なら `ApplyIfNotNull` を使う
- `OrderedAfter` は例。今の `OrderQueries` には `WithStatus` と `OrderedBefore` しかない

### C. null を受け付けるオーバーロードを `OrderQueries` に足す（非推奨寄り）

```csharp
public static IQueryable<Order> WithStatus(this IQueryable<Order> query, OrderStatus? status) =>
    status is { } s ? query.WithStatus(s) : query;
```

- 呼び出し側は一番短くなる
- `WithStatus(null)` が「絞り込まない」なのか「Status が NULL のものを探す」なのか、名前から読み取れない。Batch のように必ず値を渡す側からも紛らわしい
- 使うなら `WithStatusIfSpecified` のように意図が分かる名前にする

---

## 3. 避けたい書き方

```csharp
.Where(o => status == null || o.Status == status)
```

- 動くが、SQL に `@status IS NULL OR ...` のような形で条件が入ることがある。条件が増えると、意図も生成される SQL も読みにくくなる
- どんな SQL になるかは `query.ToQueryString()` で確認できる

## 4. 方針と残課題のまとめ

### 方針（案）

| 状況 | 書き方 |
|---|---|
| 条件が 2〜3 個 | A：`if` で再代入する（今のまま） |
| 検索画面のように任意の条件が増えてきた | B：`ApplyIfNotNull` / `WhereIf` を `Data` に置く。20261020_01 の `OrderSearchCriteria` のような条件オブジェクトと組み合わせ、リポジトリのメソッドを 1 つにする |
| null を受け付けるオーバーロード | 使わない。使うなら意図が分かる名前にする |

### 残課題

| 優先度 | 内容 | 出典 |
|---|---|---|
| 低 | 任意の条件が増える検索を作るときに、`QueryableExtensions` を `Data` に足す | 2 章の B、20261020_01 の 3 章の C |
