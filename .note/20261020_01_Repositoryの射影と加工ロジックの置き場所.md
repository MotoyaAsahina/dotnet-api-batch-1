# Repository の射影と加工ロジックの置き場所（2026-10-20）

リライト対象の Web アプリケーションでは、DB からデータを取得した後の値の変換など、業務的な加工ロジックが非常に長い。テーブルのカラム数が多いことも一因になっている。この加工を EF Core の Repository の `Select` の中で行ってよいか、エンティティで受け取って Service で加工すべきか、オーバーフェッチを避けて取得用のモデルへ直接 `Select` できるかを検討した記録です。

## 1. 現状：Response へ直接射影している

### 概要

**このプロジェクトの `OrderRepository` は、`Select` で Response の型へ直接射影している。** 加工は詰め替えと集計だけなので、この形で問題はない。

### 中身

| メソッド | 射影先 | `Select` の中でしていること |
|---|---|---|
| `GetDetailAsync` | `OrderDetailResponse` | 顧客名・商品名の結合、明細の並び替え |
| `ListByCustomerAsync` | `OrderSummaryResponse` | 明細の金額の合計（`Sum`） |

業務的な変換が長くなると、この形のままでは 2 章の問題が出る。

## 2. Select の中で加工するのが不適切な理由

### 概要

**EF Core の仕組みとしては動かせるが、避けたほうがよい。** 一番外側の `Select` に限り、SQL に変換できない C# メソッドの呼び出しが許される（その部分はクライアント側で評価される）。ただし次の問題がある。

### SQL になる部分と C# で動く部分の境目が見えない

- 「どこまでが SQL で、どこからが C# か」がコードから読み取れない
- `Trim()`・文字列比較・`null` の扱い・`decimal` の丸め・日付計算などは、SQL に変換されると C# と結果が変わることがある
- リライトで「現行と同じ結果」を求めるなら、大きなリスクになる

### エンティティを丸ごとメソッドに渡すと全カラムを取得する

- `.Select(o => Convert(o))` のように書くと、EF はエンティティ全体を組み立てるため、全カラムを取得する
- オーバーフェッチを避けたい、という目的と逆の結果になる

### インスタンスメソッドを呼ぶと実行時エラーになる

- Repository や Service のインスタンスメソッドを `Select` の中で呼ぶと、EF Core はメモリリークの恐れを理由に例外を投げる
- 使えるメソッドは static に限られる

### テストと再利用がしにくい

- 業務ロジックが `IQueryable` の式木の中にあるので、ロジックだけを単体テストできない。テストに DB（または SQLite などの代替）が必要になる
- 同じ加工を別のクエリでも使いたい場合、式を共有しにくい

### Where や OrderBy では使えない

- 加工結果で絞り込みや並び替えをしたくなった時点で、例外になる

## 3. エンティティで受け取って Service で加工する案

### 概要

**成り立つが、必須ではない。** オーバーフェッチになる。

### メリットと注意点

| メリット | 注意点・デメリット |
|---|---|
| Repository の実装が単純になる | オーバーフェッチになる |
| 追跡を使えば、そのまま更新処理に流用できる | 読み取り専用なら `AsNoTracking()` を付け忘れないこと |
| エンティティの定義だけで済み、型が増えない | `Include` を重ねると、結合結果の行数が膨れ上がる（cartesian explosion）。`AsSplitQuery()` の検討が必要 |
| | 必要なカラムが型で表現されないため、どのカラムに依存しているか追いにくい |

### オーバーフェッチの影響

影響の大きさはカラムの種類で決まる。大きな `text` / `bytea` 型のカラムが含まれていたり、一覧取得で行数が多かったりすると影響は大きい。小さな列が多いだけなら、実測すると誤差程度のこともある。測ってから判断してよい論点。

## 4. 取得用モデルへ直接 Select する案

### 概要

**できる。** エンティティではないクラスへ `Select` すると、EF はそのクラスが参照するカラムだけを SELECT 句に含める。結果は中間のエンティティを作らずに、直接そのクラスへ入る。以下、この取得用モデルを Read Model と呼ぶ。

### 例

```csharp
// Repository が返す取得用モデル（Response ではない）
public sealed class OrderDetailRow
{
    public required long Id { get; init; }
    public required string CustomerName { get; init; }
    public required OrderStatus Status { get; init; }
    public required string? RawCode { get; init; }   // 加工前の値をそのまま持つ
    // ...必要なカラムだけ
}

// Repository：取得と、SQL で行うべき処理（結合・絞り込み・集計）だけを書く
db.Orders.AsNoTracking()
    .Where(o => o.Id == id)
    .Select(o => new OrderDetailRow
    {
        Id = o.Id,
        CustomerName = o.Customer.Name,
        Status = o.Status,
        RawCode = o.Code,
    })
    .FirstOrDefaultAsync(ct);

// Service / Converter：業務的な加工。DB なしで単体テストできる
public static OrderDetailResponse ToResponse(OrderDetailRow row) => ...;
```

### 注意点

- メモリ上での変数の移し替えは起きない。ただし `Id = o.Id` のような対応関係の記述は残る
- カラム数が多いときは、`record` の位置指定コンストラクターより、`required` + `init` のプロパティのほうが対応を取り違えにくい

## 5. 対応関係の記述を減らす方法

### 概要

**カラム数が多いときは、手書きの `Select` か Mapperly がよい。** 手書きは型安全で明示的、Mapperly は記述量を減らせる。現行の SQL が複雑で、そのまま移したい箇所に限って `SqlQuery<T>` を使う組み合わせも現実的。

### 選択肢

| 方法 | 内容 | 注意点 |
|---|---|---|
| Mapperly（ソースジェネレーター） | `IQueryable` への射影（`ProjectToXxx`）をコンパイル時に自動生成する | 生成されたコードを確認できて実行時の驚きが少ない。複雑な変換は手書きが必要 |
| AutoMapper `ProjectTo` / Mapster `ProjectToType` | 実行時に射影の式を組み立てる | 対応漏れが実行時まで分からない。AutoMapper は v15 から商用ライセンス |
| `Database.SqlQuery<T>(...)`（EF Core 8 以降） | 生 SQL の結果を、エンティティ登録していない型へ、カラム名で対応付ける | 現行システムの SQL を流用しやすいのは、リライトでは大きな利点。ただし文字列の SQL なので型チェックが効かない |
| Keyless エンティティ + `ToView` / `ToSqlQuery` | DB のビューや SQL を読み取り専用のエンティティとして扱う | ビューの管理が DB 側に移る |
| Dapper を併用 | 読み取り専用のクエリだけ Dapper で書く | 2 つのデータアクセス方式が共存し、運用ルールが必要になる |

## 6. 方針とトレードオフのまとめ

### 方針

| 項目 | 方針 |
|---|---|
| 全体の流れ | Repository が Read Model へ `Select` する → Service（または専用の Converter）が Response へ加工する → クライアントに返す |
| Repository の責務 | SQL で行うべきこと（結合・絞り込み・並び替え・ページング・集計）に絞り、加工前の値を Read Model に詰めて返す。`Select` の中では業務的な変換をしない |
| 加工ロジックの置き場 | Service に直接書くと長くなるので、`OrderDetailConverter` のような副作用のない static 関数、またはクラスに切り出す。Service はそれを呼んで組み立てる役に徹する。現行システムとの結果比較テストを DB なしで大量に書ける |
| 使い分け | 加工が単純な画面は、今の `OrderRepository` のように Response へ直接射影してよい。「業務的な加工が入るなら Read Model を経由する」のような基準をチームで決めておく |
| 参照系と更新系の分離（CQRS 寄り） | 参照系は Repository ではなく Query Service として、Read Model を返す専用の層にする方法もある。更新系だけ集約単位の Repository とエンティティを使う |

### 各方式のトレードオフ

| 方式 | 取得カラム | ロジックのテストしやすさ | 型・記述量 | 主なリスク |
|---|---|---|---|---|
| `Select` の中で加工して Response を返す | 最小 | 低（DB が必要） | 少 | SQL 変換で結果がずれる、static 制約、`Where` で使えない |
| エンティティで取得し Service で加工 | 過剰 | 高 | 少 | オーバーフェッチ、`Include` による行数の膨張 |
| Read Model に射影し Service で加工 | 最小 | 高 | 型が増える | 対応関係の記述量（Mapperly で軽減できる） |
| `SqlQuery<T>` で Read Model に取得 | 最小 | 高 | SQL を流用できる | 型チェックが効かない、カラム名がずれると失敗する |
