## 1. 現状：トランザクションを使っている箇所

### 概要

**明示的なトランザクションはない。** `BeginTransaction` や `TransactionScope` は、リポジトリ以外も含めてどこにも出てこない。トランザクションは、EF Core が `SaveChanges` のたびに自動で張るものだけ。

### リポジトリの中身

| リポジトリ | メソッド | 内容 |
|---|---|---|
| `CustomerRepository` | `ExistsAsync` | `AnyAsync` で存在を確認する。読み取りのみ |
| `ProductRepository` | `ListAsync` / `ListByIdsAsync` | `AsNoTracking` の参照のみ |
| `OrderRepository` | `GetDetailAsync` / `ListByCustomerAsync` | `AsNoTracking` の参照 |
| | `Add` / `SaveChangesAsync`（対応前） | 唯一の書き込み。`SaveChangesAsync` は `db.SaveChangesAsync` を呼ぶだけ |

### 暗黙のトランザクション

- `OrderService.CreateAsync` は、`Order` と `Items` を同じ `SaveChangesAsync` で保存している。EF Core は 1 回の `SaveChanges` の中の変更をまとめて 1 つのトランザクションで実行するので、注文本体と明細が片方だけ保存されることはない
- 1 テーブルに 1 行だけ INSERT するときは、SQL が 1 文なので EF Core はトランザクションを張らない（既定の `AutoTransactionBehavior.WhenNeeded`）。1 文の SQL はそれだけで原子的なので、結果は同じ

### トランザクションの外で行われていること

`CreateAsync` の次の処理は、どれも保存とは別の SQL で、トランザクションの外にある。

| 処理 | 場所 |
|---|---|
| 顧客が存在するかの確認 | `OrderService.cs` の `customers.ExistsAsync` |
| 商品の存在確認と単価の取得 | `OrderService.cs` の `products.ListByIdsAsync` |

## 2. 確認と保存の間に削除された場合

### 概要

**DB の整合性は保たれるが、レスポンスは 500 になる。**

### 動き

1. `db/init/01_schema.sql` で、`orders.customer_id` と `order_items.product_id` に `REFERENCES`（外部キー制約）が付いている
2. 確認の後に顧客や商品が削除されると、注文の INSERT が外部キー違反（SqlState `23503`）で失敗し、`DbUpdateException` になる。存在しないものを参照する注文は保存されない
3. `AppExceptionHandler.Map()` が `DbUpdateException` を特別扱いするのは、一意制約違反（`23505` → 409）だけ。`23503` は最後の分岐に入り、500 / `INTERNAL_SERVER_ERROR` になる。ログは `LogError` で、スタックトレース付き
4. 期待する応答は、事前の確認で見つかったときと同じ 400 / `VALIDATION_ERROR`。500 にはならないほうがよい

### 実際に起きるか

API にもバッチにも、顧客や商品を削除する処理は今のところない。起きるのは DB を直接操作した場合だけ。

## 3. 削除を防ぐ方法の選択肢

### 概要

要件によって選ぶ。「確認した値をそのまま確実に使いたい」ならロック、「存在しないものを参照させなければよい」なら外部キー制約とエラーの変換。**今の要件なら後者でよい。**

### トランザクションだけでは防げない

PostgreSQL の既定の分離レベル（READ COMMITTED）では、普通の `SELECT` は行をロックしない。トランザクションの中で確認しても、その後に別の処理が `DELETE` できる。削除を止めるには、確認する `SELECT` で行ロックを取る必要がある。

| ロック | 削除 | 単価の更新 |
|---|---|---|
| `FOR KEY SHARE` | 防ぐ | 許す |
| `FOR SHARE` | 防ぐ | 防ぐ |

「取得した単価で保存するまで単価も変えさせない」なら `FOR SHARE`。

### 選択肢

| 方法 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 行ロック | トランザクションの中で `SELECT ... FOR SHARE` で確認し、そのまま保存する | 確認した値（単価も）がそのまま使えることを保証できる | LINQ で書けない（5 章）。実行戦略で包む必要がある。デッドロックを避けるため ID 順にロックする |
| B. 外部キー制約に任せる | 今のまま。INSERT のときに PostgreSQL が参照先の行を `FOR KEY SHARE` 相当でロックして確認する。違反をエラーレスポンスに変換する | 既存の実装で整合性は保たれている。`Map()` に分岐を足すだけ | 単価が確認後に変わっても、取得した時点の値で保存される |
| C. SERIALIZABLE | 分離レベルを上げ、ロックなしで競合を検出する | ロックを書かなくてよい | 競合はシリアライズエラー（`40001`）になるので、やり直しの仕組みが必要 |
| D. 論理削除 | 顧客や商品を物理的に削除せず、削除フラグなどで扱う | 注文の明細は商品を参照し続けるので、実務でよく使われる | 参照するクエリすべてで、削除済みを除く条件が必要 |

競合はほとんど起きないので、実務では B がよく選ばれる。

### B を採るときのステータス（未実装）

| 案 | 意味 | 実装 |
|---|---|---|
| 409 `CONFLICT` | 「ほかの更新と競合した」。一意制約違反・楽観ロックの分岐と同じ考え方 | `Map()` に `PostgresErrorCodes.ForeignKeyViolation` の分岐を 1 つ足す |
| 400 `VALIDATION_ERROR` | 事前の確認で見つかった場合と同じ応答。クライアントから見ると、タイミングで応答が変わらない | 項目名（`customerId` / `items`）まで合わせるには、`PostgresException.ConstraintName` から項目名を割り出す必要がある |

ほとんど起きない競合のための分岐なので、まずは汎用的な 409 にするのがよい。20261019_02 の残課題「外部キー制約の違反（`23503`）を 409 にするか決める」と同じ件。

## 4. EF Core の保存の仕組み

### `Add` と `SaveChangesAsync` の役割

| 呼び出し | 何が起きるか |
|---|---|
| `orders.Add(order)`（中身は `db.Orders.Add`） | エンティティを `DbContext` の変更追跡に「追加予定（Added）」として登録するだけ。**DB には何も送らない** |
| `SaveChangesAsync` | 変更追跡に溜まった変更から INSERT / UPDATE / DELETE を作り、DB で実行する |

- `Add` だけでは、1 テーブルでも何も保存されない。2 テーブルにまたがるかどうかは関係ない
- `order.Id` は DB が採番するので、`SaveChangesAsync` の後でないと決まらない

### `OrderItem.OrderId` に値が入る仕組み

**関連の定義**：`Data/Orders/OrderConfiguration.cs`

```csharp
builder.HasMany(o => o.Items)          // Order は複数の Items を持つ
    .WithOne(i => i.Order)             // OrderItem は 1 つの Order に属する
    .HasForeignKey(i => i.OrderId)     // その外部キーは OrderItem.OrderId
    .OnDelete(DeleteBehavior.Cascade);
```

- `AppDbContext.OnModelCreating` の `ApplyConfigurationsFromAssembly` で読み込まれる
- この設定がなくても、EF Core は命名規約から同じ関連を見つける。`Order.Items` と `OrderItem.Order` が互いを指しており、「ナビゲーション名 + `Id`」の `OrderId` があるため。`OrderItem.Product` / `ProductId` は設定がなく、規約だけで決まっている。必須の関連なので、規約でも既定は Cascade

**値が入るタイミング**

1. `OrderService` は明細を `order.Items` に入れるだけで、`OrderId` には何も入れない
2. `Add(order)` で、EF Core は `Items` をたどって明細も Added にする。`Order.Id` はまだないので、仮の値でつないでおく
3. `SaveChangesAsync` で `orders` を INSERT し、採番された ID を `order.Id` と各明細の `OrderId` に入れてから `order_items` を INSERT する。この書き戻しを「fixup」と呼ぶ

## 5. EF Core で自分でトランザクションを扱うときの注意

### ロック句を付ける LINQ がない

EF Core の LINQ は DB に依存しない書き方を前提にしているが、ロックの書き方と意味は DB ごとに違う。

| DB | 書き方 |
|---|---|
| PostgreSQL / MySQL | `SELECT ... FOR UPDATE` / `FOR SHARE` |
| SQL Server | `FROM t WITH (UPDLOCK, ROWLOCK)` のようなテーブルヒント |
| SQLite | 行ロックがない |

- LINQ は `Include` や `Join` を含む SQL にもなるので、ロック句の意味を一律に決められない。たとえば PostgreSQL では、外部結合の NULL になりうる側に `FOR UPDATE` を付けるとエラーになる
- ロックはトランザクションの中でしか意味を持たない
- EF Core は、同時実行の制御には楽観的同時実行制御（同時実行トークン）を標準にしている。`AppExceptionHandler` の `DbUpdateConcurrencyException` → 409 は、その仕組みに対応したもの
- 悲観ロックが必要なときの書き方
  - `FromSql($"SELECT * FROM products WHERE id = ANY({ids}) FOR SHARE")` のように SQL を書く
  - `TagWith("FOR UPDATE")` で目印を付け、`DbCommandInterceptor` で SQL の末尾にロック句を足す

### `EnableRetryOnFailure()` と自分で開始するトランザクション

`Data/ServiceCollectionExtensions.cs` で `EnableRetryOnFailure()` を有効にしている。一時的な障害で失敗した処理を EF Core がやり直す仕組み。

- `SaveChangesAsync` 1 回なら、それだけで完結しているので、やり直しても問題ない
- 自分で開始したトランザクションの中で接続が切れると、トランザクション全体（ロックも含む）がロールバックされる。失敗した処理だけをやり直すと、ロックのない状態で保存することになる。EF Core にはどこからやり直せばよいか分からないので、やり直さずに `InvalidOperationException` を投げる（トランザクションの中で最初にクエリや `SaveChanges` を実行した時点）
- 対応は、トランザクション全体を実行戦略に「やり直しの単位」として渡すこと

```csharp
var strategy = db.Database.CreateExecutionStrategy();
await strategy.ExecuteAsync(async ct =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);
    // 確認・INSERT など
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}, cancellationToken);
```

- 失敗するとラムダ全体が最初から実行し直されるので、何度実行しても同じ結果になるように書く。エンティティはラムダの中で作るか、`ChangeTracker.Clear()` で前回の状態を消してから始める

### 複数リポジトリで書き込むときに `BeginTransactionAsync` が必要か

**多くの場合は不要。** `AddDbContext` で登録した `AppDbContext` は Scoped で、リポジトリもすべて Scoped なので、1 リクエストの中ではどのリポジトリも同じ `DbContext` を共有している。複数のリポジトリで `Add` や更新をしても、最後に `SaveChangesAsync` を 1 回呼べば 1 つのトランザクションで保存される。

`BeginTransactionAsync` が必要になるのは次の場合。

| 場合 | 理由 |
|---|---|
| `SaveChangesAsync` を 2 回以上呼ぶ | 途中で採番された ID を使って別の処理をするなど。1 回ごとに別のトランザクションになる |
| `ExecuteUpdateAsync` / `ExecuteDeleteAsync` / 生 SQL と `SaveChangesAsync` を混ぜる | 前の 3 つは変更追跡を通らず、その場で実行される |
| ロック付きの SELECT と書き込みを同じトランザクションに入れる | 3 章の A |
| 分離レベルを指定する | 3 章の C |

## 6. 対応内容：Unit of Work の導入

### 概要

対応前は `SaveChangesAsync` が `IOrderRepository` にあった。`SaveChangesAsync` は `DbContext` 全体の変更を保存するので、ほかのリポジトリでも書き込むようになると「注文リポジトリの `SaveChangesAsync` が顧客の変更まで保存する」という分かりにくい形になる。保存をリポジトリから切り出し、Unit of Work（`IUnitOfWork`）にした。

### 変更したファイル

| ファイル | 内容 |
|---|---|
| `Api/Persistence/UnitOfWork.cs`（新規） | `IUnitOfWork`（`SaveChangesAsync` のみ）と、`AppDbContext.SaveChangesAsync` を呼ぶ `UnitOfWork` |
| `Api/Features/Orders/OrderRepository.cs` | `SaveChangesAsync` を削除した。`Add` に「保存は `IUnitOfWork` で行う」とコメントを付けた |
| `Api/Features/Orders/OrderService.cs` | コンストラクターで `IUnitOfWork` を受け取り、`Add` の後に `unitOfWork.SaveChangesAsync` を呼ぶ |
| `Api/Program.cs` | `AddScoped<IUnitOfWork, UnitOfWork>()` で登録した |
| `tests/DotnetApiBatch.Api.Tests/Features/Orders/OrderServiceTests.cs` | `IUnitOfWork` をモックにし、保存の確認を `_orders` から `_unitOfWork` に変えた。`Received.InOrder` で `_orders.Add` → `_unitOfWork.SaveChangesAsync` の順を確認する |
| `README.md` | リポジトリの一覧、API の構成、更新の書き方に Unit of Work を追記した |

### 確認したこと

- ビルドは警告 0・エラー 0、テストは 13 件（`Data.Tests` 5 件、`Api.Tests` 8 件）すべて成功
- `OrderService` から `unitOfWork.SaveChangesAsync` の呼び出しを消すと、`CreateAsync_saves_pending_order_with_current_unit_prices` が失敗することを確認した
- ローカルの DB に対して API を起動し、`POST /orders`（明細 2 件）が 201 を返し、`GET /orders/{id}` で注文と明細が保存されていることを確認した

### 選択肢と注意点

- **置き場所**：`Api/Persistence/` に置いた。README の方針で、リポジトリとサービスは Api と Batch で共有しない。Batch は `ExecuteUpdateAsync` で更新していて `SaveChangesAsync` を使わないので、今は Api だけに置いた。Batch でも必要になったら、`Data` に移して `AddData` で登録する
- **フォルダー名**：`Data` は `DotnetApiBatch.Data` と紛らわしいので避けた。`Features/` はドメインごとのフォルダーなので、ドメインに属さないものは置かなかった
- **持たせるメソッド**：`SaveChangesAsync` だけにした。トランザクションの開始（`BeginTransactionAsync`）は、5 章のとおり実行戦略で包む必要があり、使う場面もまだない。必要になったら、`ExecuteInTransactionAsync(Func<CancellationToken, Task>)` のように、実行戦略とトランザクションをまとめて扱うメソッドを足す
- **`AppDbContext` 自体を `IUnitOfWork` にする方法**：`AppDbContext : IUnitOfWork` にすれば、クラスを 1 つ減らせる。ただし `Data` が Api のインターフェースを知る必要があり、依存の向き（Api → Data）に反するので採らなかった

### 採用判断

**実施済み。** ブランチ `feature/unit-of-work` で PR を作成した。外部キー違反のレスポンス（3 章）は未実装。

## 7. 決定事項と残課題のまとめ

### 決定事項

| 項目 | 決定内容 |
|---|---|
| 保存 | リポジトリは `SaveChangesAsync` を持たない。サービスが `IUnitOfWork.SaveChangesAsync` を 1 回呼ぶ |
| 複数リポジトリでの書き込み | 同じ `AppDbContext` を共有するので、`SaveChangesAsync` 1 回で 1 つのトランザクションになる。`BeginTransactionAsync` は 5 章の場合だけ使う |
| 確認と保存の間の削除 | 行ロックは使わず、外部キー制約に任せる（3 章の B） |
| 自分で開始するトランザクション | 使うときは `CreateExecutionStrategy().ExecuteAsync` で包む |

### 残課題

| 優先度 | 内容 | 出典 |
|---|---|---|
| 低 | 外部キー制約の違反（`23503`）を 409 `CONFLICT` にする（400 にするなら `ConstraintName` から項目名を割り出す）。合わせて 20261019_03 のテスト A4 の期待値を変える | 3 章、20261019_02 の残課題 |
| 低 | 顧客・商品を削除する機能を作るときに、物理削除か論理削除かを決める | 3 章の D |
| 低 | トランザクションが必要になったら、`IUnitOfWork` に実行戦略とトランザクションをまとめたメソッドを足す | 6 章 |
| 低 | 依存ルールのテストに「サービスは `AppDbContext` を直接使わない」を加える | 6 章、20261018_01 の残課題 |
