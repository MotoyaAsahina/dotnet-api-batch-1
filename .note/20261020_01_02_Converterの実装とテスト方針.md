## 1. Converter を DI してモックするか

### 概要

**副作用のない Converter は、DI もモックもしない。** Service のテストでは本物の Converter を使う。モックにするのは、DB・外部 API・現在時刻のように、テストで結果が定まらないものや遅いものだけ。[20261019_01 の 3 章](20261019_01_単体テストのしやすさ.md#3-どこをインターフェースにするか)の「Repository は DB との境界なのでインターフェースにする。Service は基本しない」と同じ考え方。

### Converter をモックしないほうがよい理由

| 理由 | 内容 |
|---|---|
| テストが検証する内容が弱くなる | モックが返した値を Service がそのまま返したことしか確認できず、「正しい Response ができたか」を確認しなくなる |
| 実装の細部にテストが縛られる | 「Converter の `ToResponse` が呼ばれたか」を検証すると、変換を Service 内に戻すなどの整理をしただけでテストが壊れる |
| 型だけが増える | `IOrderDetailConverter` と実装の 2 つの型が、変換 1 つごとに増える |
| モックにする必要がない | 純粋な関数は速く、結果も毎回同じなので、そのまま使っても単体テストの条件を満たす |

Converter が現在時刻や設定値に依存する場合は、3 章・4 章の形にする。

## 2. 例 1：純粋な Converter（基本形）

### 概要

**Read Model を Response に変えるだけなら、static クラスで十分。** Service はコンストラクターで受け取らず、直接呼ぶ。

### 実装

```csharp
// Features/Orders/OrderReadModels.cs
public sealed class OrderDetailRow
{
    public required long Id { get; init; }
    public required string CustomerName { get; init; }
    public required OrderStatus Status { get; init; }
    public required DateTime OrderedAt { get; init; }
    public required IReadOnlyList<OrderItemRow> Items { get; init; }
}

public sealed class OrderItemRow
{
    public required string ProductName { get; init; }
    public required int Quantity { get; init; }
    public required decimal UnitPrice { get; init; }
}
```

```csharp
// Features/Orders/OrderDetailConverter.cs
public static class OrderDetailConverter
{
    public static OrderDetailResponse ToResponse(OrderDetailRow row) => new(
        row.Id,
        row.CustomerName.Trim(),   // 現行の加工を C# 側で再現する
        row.Status,
        row.OrderedAt,
        Total: row.Items.Sum(i => i.Quantity * i.UnitPrice),
        Items: row.Items.Select(ToItem).ToList());

    private static OrderItemResponse ToItem(OrderItemRow item) =>
        new(item.ProductName, item.Quantity, item.UnitPrice);
}
```

```csharp
// OrderService：Converter はコンストラクターで受け取らず、直接呼ぶ
public async Task<OrderDetailResponse> GetDetailAsync(long id, CancellationToken cancellationToken)
{
    var row = await orders.GetDetailAsync(id, cancellationToken)
        ?? throw new NotFoundException("注文", id);
    return OrderDetailConverter.ToResponse(row);
}
```

### テスト

テストは 2 種類に分ける。

| テスト | 対象 | 書き方 |
|---|---|---|
| Converter のテスト | 変換の細かいケース | DB もモックも使わず、網羅的に書く。現行システムとの突き合わせ（同じ入力で同じ出力になるか）もここに書く |
| Service のテスト | 取得から変換までの流れ | モックするのは Repository だけ。Converter は本物を通し、少数の代表ケースだけ確認する |

```csharp
public class OrderDetailConverterTests
{
    [Fact]
    public void ToResponse_sums_quantity_times_unit_price()
    {
        var row = Row(items: [Item(quantity: 2, unitPrice: 100m), Item(quantity: 1, unitPrice: 50m)]);

        var result = OrderDetailConverter.ToResponse(row);

        Assert.Equal(250m, result.Total);
    }

    [Theory]
    [InlineData("  山田 太郎 ", "山田 太郎")]
    [InlineData("山田　太郎", "山田　太郎")]   // 全角スペースの扱いが現行と同じか確認する
    public void ToResponse_trims_customer_name(string raw, string expected) { /* ... */ }
}
```

```csharp
// OrderServiceTests
[Fact]
public async Task GetDetailAsync_converts_row_to_response()
{
    _orders.GetDetailAsync(1, Arg.Any<CancellationToken>()).Returns(Row(id: 1, items: [Item(2, 100m)]));

    var result = await _sut.GetDetailAsync(1, CancellationToken.None);

    Assert.Equal(1, result.Id);
    Assert.Equal(200m, result.Total);
}
```

## 3. 例 2：時刻や設定に依存するときは引数で渡す

### 概要

**値は Service が集め、Converter には引数で渡す（第一候補）。** Converter は純粋なままになる。例として「注文から 24 時間以内で、かつ `Pending` ならキャンセルできる」という判定を加える。Converter の中で `DateTime.UtcNow` を読むと、結果が実行時刻で変わり、テストできない。

### 実装

```csharp
public static class OrderDetailConverter
{
    private static readonly TimeSpan CancelableWindow = TimeSpan.FromHours(24);

    public static OrderDetailResponse ToResponse(OrderDetailRow row, DateTime now) => new(
        // ...
        CanCancel: row.Status == OrderStatus.Pending && now - row.OrderedAt < CancelableWindow);
}

// Service：TimeProvider は今と同じく Service が受け取る
return OrderDetailConverter.ToResponse(row, timeProvider.GetUtcNow().UtcDateTime);
```

### テスト

境界値をそのまま引数で指定できる。

```csharp
[Theory]
[InlineData(23, true)]
[InlineData(24, false)]
public void ToResponse_can_cancel_within_24_hours(int elapsedHours, bool expected)
{
    var orderedAt = new DateTime(2026, 10, 20, 0, 0, 0, DateTimeKind.Utc);
    var row = Row(status: OrderStatus.Pending, orderedAt: orderedAt);

    var result = OrderDetailConverter.ToResponse(row, orderedAt.AddHours(elapsedHours));

    Assert.Equal(expected, result.CanCancel);
}
```

### マスタデータが必要な場合

コードの名称など、マスタデータが必要な場合も同じ。Service が Repository からマスタを取得し、`IReadOnlyDictionary<string, string>` として Converter に渡す。Converter の中から DB を読みに行かない。

## 4. 例 3：依存が多いときはクラスにして DI する

### 概要

**税率・端数処理・表示形式など、設定値が増えて引数が膨らむ場合は、Converter をクラスにして DI する。** DI するのは依存（設定や時刻）を組み立てるためで、モックするためではない。インターフェースは作らず、テストでも本物を作る。

### 実装

```csharp
public sealed class PricingOptions
{
    public required decimal TaxRate { get; init; }
    public required MidpointRounding Rounding { get; init; }
}

public sealed class OrderDetailConverter(IOptions<PricingOptions> options, TimeProvider timeProvider)
{
    private readonly PricingOptions _pricing = options.Value;

    public OrderDetailResponse ToResponse(OrderDetailRow row)
    {
        var subtotal = row.Items.Sum(i => i.Quantity * i.UnitPrice);
        var tax = Math.Round(subtotal * _pricing.TaxRate, 0, _pricing.Rounding);
        var now = timeProvider.GetUtcNow().UtcDateTime;
        return new OrderDetailResponse(/* ... */ Total: subtotal + tax, CanCancel: /* now を使う */);
    }
}
```

```csharp
// 登録：状態を持たないので Singleton でよい（依存も Singleton のものだけにする）
services.Configure<PricingOptions>(configuration.GetSection("Pricing"));
services.AddSingleton<OrderDetailConverter>();

// Service：具象クラスのまま受け取る
public class OrderService(
    IOrderRepository orders,
    OrderDetailConverter converter,
    /* ... */)
```

### テスト

モックではなく、本物を `FakeTimeProvider` と固定の設定で組み立てる。

```csharp
public OrderServiceTests()
{
    var time = new FakeTimeProvider(Now);
    var converter = new OrderDetailConverter(
        Options.Create(new PricingOptions { TaxRate = 0.1m, Rounding = MidpointRounding.ToZero }),
        time);
    _sut = new OrderService(_customers, _products, _orders, _unitOfWork, converter, time);
}
```

### 注意点

- Singleton で登録するなら、Scoped のもの（`AppDbContext` や Repository）を受け取ってはいけない
- Scoped のものを受け取りたくなったら、それは I/O が Converter に入り込んでいるサイン。3 章の形に戻し、値は Service が集めて渡す

## 5. 方針のまとめ

### 使い分け

| Converter の状態 | 形 | Service への渡し方 | テストでの扱い |
|---|---|---|---|
| 入力だけで結果が決まる | static クラス（2 章） | 渡さない。直接呼ぶ | 本物を使う |
| 時刻・設定・マスタが少し必要 | static ＋ 引数（3 章） | 渡さない。値を引数で渡す | 本物を使う。値は引数で固定する |
| 設定などの依存が多い | クラス（4 章） | コンストラクターで具象クラスを受け取る | 本物を、固定した依存で組み立てる |
| DB・外部 API を呼ぶ必要がある | Converter にしない | その部分は Repository やクライアントに切り出し、そちらをインターフェースにする | 切り出した側をモックする |

### 方針

| 項目 | 方針 |
|---|---|
| インターフェースとモック | 作るのは I/O をする側（Repository や外部 API のクライアント）だけ。Converter には作らない |
| Converter に入れないもの | DB や外部 API の呼び出し、`DateTime.UtcNow` の直接参照 |
| テストの分担 | 変換の網羅は Converter のテスト、流れの確認は Service のテスト（代表ケースのみ） |
| 例外 | 変換が非常に重い場合（大量の行を変換するなど）は、Service のテストを軽くするためにモックすることもある。その場合でも、多くはテストデータの件数を絞るだけで足りる |
